## 요약

1. 우리 배치 엔진 3종과 설정 변종 7열 · 스케줄 배치 순서 2열, 대조군 6열을 **같은 가상 클러스터(판) · 같은 워크로드 표본 · 같은 제약** 위에서 돌려 지표 15개로 나란히 냅니다. 응답은 승자를 지명하지 않습니다 — 셀마다 값과 유효 여부·사유만 싣고, 판정은 사람이 판 이름·전원 가정·부하율과 함께 씁니다.
2. 전력·온도는 **엔진의 모델이 아니라 판 파일의 생성식**으로 계산합니다. 엔진의 목적 함수로 평가하면 우리 엔진이 1등인 것이 정의상 당연해지기 때문입니다. 다만 생성식도 실측이 아닌 가정이라, 확인되는 것은 "엔진 가정과 생성식이 얼마나 다른가"까지입니다.
3. 판이 10장인 이유는 한 판으로는 반론을 막을 수 없기 때문입니다 — 주 결과판, 우리 엔진이 지도록 만든 반증판, 센서 공백판, 엔진 가정이 틀린 방향으로 기울인 판 3장(볼록·정격 어긋남·둘 다), 링크 판, 위상 독립 짝 2장, 오목 판.
4. 판정은 **판정판의 한 셀**(부하율 60% · 전원 제어 가정)에서만, 결과보다 먼저 고정한 규칙(짝 지점 ≥ 10 · 격차 중앙값 2.0%p 이상 축소 · 지점의 10/12 이상 축소 · 주 결과판에서 방향 일치)으로 합니다. 결말은 판정 불가 · 성공 · 실패 세 가지이고 실패도 게시합니다.
5. 규칙은 코드 상수로 두고 테스트가 다이제스트로 봉인합니다. 규칙을 바꾸는 커밋은 `rules:` 로 시작하고 결과 코드와 같은 커밋에 담지 않습니다. 결과를 보고 규칙을 고친 경우(사후 개정)는 숨기지 않고 이력에 적습니다.
6. 이 API 는 전력 기반 배치·온도 제어의 효과를 **결론 수준으로 증명하지 않습니다.** 배포 환경은 실존 노드가 한 대라 실환경 비교가 성립하지 않습니다.

## 1. 목적과 범위

**목적.** 스케줄러가 고른 배치가 단순한 규칙(선착순 · 자원 최밀집 · 무작위 등)보다 전력·열 측면에서 나은지, 어떤 조건에서 그렇지 않은지를 **같은 입력 위에서** 재는 것입니다. 운영 중인 클러스터는 노드가 한 대뿐이라 비교가 성립하지 않으므로, 노드 14대 규모의 가상 클러스터를 파일로 정의해 씁니다.

**범위에 들어가는 것.**
- 운영 엔진 3종(`power` · `temperature` · `weighted`)과 그 설정 변종, 비교 전용 대조군(4장).
- 부하율 4단계 × 전원 상태 가정 2종의 격자에서 지표 15개(5~6장).
- 다음 엔진 변경의 효과를 판정하는 규칙과 그 기준선(8~9장).

**범위 밖.**
- 실제 서버의 전력·온도 측정. 값은 전부 판 파일의 생성식 출력입니다(2장 · 11장).
- 승자 선정. 응답에 승자 필드를 두지 않습니다 — API 가 승자를 계산하면 그 필드만 인용되고, 판 이름·전원 가정·부하율에서 떨어지는 순간 거짓이 되기 때문입니다.
- 저장소 쓰기. 워크로드는 분포 파일에서 뽑은 비영속 객체, 정책은 코드 기본값의 사본, 노드는 판 파일의 스냅샷입니다. 저장된 워크로드를 쓰면 예약 경로가 같은 워크로드를 두 번 세고, 활성 정책 조회는 정책이 없으면 기본 정책을 새로 넣는 부작용이 있습니다.
- 대조군의 운영 경로 진입. 대조군은 엔진 인터페이스(`SchedulingEngine`)를 구현하지 않는 record(`PlacementStrategy`)라 엔진 레지스트리에 수집되지 않습니다. 수집되면 엔진 id 검증이 열려 스케줄이 대조군으로 실배치할 수 있습니다.

## 2. 평가 방식

### 2.1 평가자를 엔진에서 분리한다

평가자(`GroundTruthOracle`)는 판 파일 머리말에 적힌 생성식으로 전력과 온도를 계산합니다. 클래스 이름의 영어 뜻과 달리 **실측이 아니라 "엔진 모델의 반대편"** 이라는 뜻입니다.

배치 비교의 주 지표로 엔진의 한계 전력(`PowerModel.realMarginalPower`)을 쓰면, 그것은 우리 전력 엔진 총점의 한 항을 그대로 합한 값이 됩니다(가중치 0.35 × `marginalScore`, `marginalScore = 1 − realMarginalPower / S`, S 는 W 눈금 기본 500). 목적 함수를 평가 함수로 쓰면 어떤 전략을 넣어도 그 목적 함수를 최대화한 전략이 이기므로, 우리 전략이 1등인 것은 발견이 아니라 정의가 됩니다. 그래서 평가자만 다른 식을 봅니다.

| 항목 | 생성식 |
|---|---|
| 전력 | `idleWatts + (capacityWatts − idleWatts) × (CPU사용률/100)^β` — β 는 판 파일의 `powerExponent`(기본 1 = 선형) |
| 온도 | `baseTemperature + 0.3 × CPU사용률` |

엔진은 판 파일의 `idleWatts` 를 직접 읽지 않습니다. 다만 선형 판에서는 실측 전력과 CPU 사용률로 유휴 전력을 역산하면 선언값이 복원되므로 **수치까지 독립인 것은 아닙니다** — 정보 경로가 분리됐다는 뜻이지 결과가 실물에서 성립한다는 뜻이 아닙니다.

### 2.2 전원 상태 가정 두 가지로 회계한다

배치가 전력을 얼마나 늘리는지는 전원 상태 가정에 따라 답이 다릅니다. 배치 결정은 한 번만 내리고, 같은 결정을 두 가정으로 회계합니다(배치를 두 번 돌리지 않습니다 — 두 번 돌리면 같은 결정이 나온다는 것을 우연에 맡기게 됩니다).

| 전원 가정(`PowerControl`) | 뜻 | 통합으로 아끼는 전력 |
|---|---|---|
| `AVAILABLE` | **가정** — 쓰지 않는 노드는 꺼져 있고, 빈 노드에 처음 얹으면 그 노드의 유휴 전력이 통째로 새로 듭니다 | 이 가정에서만 보입니다 |
| `UNAVAILABLE` | **현 시스템의 사실** — 노드 전원을 끄는 수단도 워크로드를 옮기는 수단도 없어, 배치의 증분은 동적분뿐입니다 | 정의상 0 |

엔진이 스스로 믿은 비용(`engineBelievedCostW`)은 엔진 노브로 계산한 값을 그대로 싣습니다 — 엔진의 믿음을 재는 값이라 평가자가 대신 정하면 안 됩니다. 생성식 값과의 차가 곧 엔진 가정과 생성식의 격차입니다.

## 3. 비교 판

판(board)은 노드 구성·생성식 지수·위상 seed·링크를 담은 가상 클러스터 파일입니다. 등록부(`BenchmarkClusters.BOARDS`) 한 곳에 순서·파일·역할이 있고, 그 순서가 응답의 판 순서입니다. 응답의 `boards[].digest` 는 파일 내용의 해시(SHA-256 앞 12자, 개행 정규화)라 표의 숫자가 어느 파일에서 나왔는지 대조할 수 있습니다.

| 판 id | 역할 | 주 결과판과의 차이 | 판정 자격 |
|---|---|---|---|
| `main` | **주 결과판** — 노드 14대 전수 계측(유휴 5 · 가동 9). 유휴 전력 비율을 0.20~0.45 로 흩뿌려 엔진 가정(정격의 30%)과 어긋나게 두고, 정격과 코어당 전력의 상관을 −0.21 로 둠 | — | 방향 판 |
| `adversarial` | **반증판** — 우리 엔진이 지도록 설계. 유휴 비율 0.060~0.100 이라 엔진이 깨우기 비용을 3~5배 과대 추정 | 노드 구성이 다름 | 없음 |
| `sparse` | **계측 공백판** — 14대 중 5대만 센서 없음(`ipmi: false`, 가동 3 · 유휴 2) | `ipmi` 플래그만 | 없음 |
| `convex` | **볼록 생성식판** — 생성식 지수 1.6 | 생성식 지수만 | 없음 |
| `misrated` | **정격 어긋남판** — 엔진에 알려 준 정격(`believedCapacityWatts`)만 ±10% | 알려 준 정격만 | 없음 |
| `convex-misrated` | **판정판** — 볼록 생성식 + 정격 어긋남 | 둘 다 | 판정 셀(부하율 60% · `AVAILABLE`) |
| `link` | **링크 판** — 주 결과판 노드 + `links:` 절 + 데이터 MDC 순환 배정. 링크 점수를 섞는 엔진은 `weighted` 뿐이라 `weighted` · `weighted-affinity` 쌍으로 링크 점수 경로의 작동을 확인하고, 지역성 효과는 원격 MDC 배치 비율(6장)로 읽음 | 링크 절·배정만 | 없음 |
| `main-independent` | 주 결과판의 **위상 독립 짝** — `phaseMode: independent` · seed 3 | 위상 방식·seed 만 | 없음(부수 보고) |
| `convex-misrated-independent` | 판정판의 위상 독립 짝 | 위상 방식·seed 만 | 없음(부수 보고) |
| `concave` | **오목 생성식판** — 생성식 지수 0.625 = 1/1.6 | 생성식 지수만 | 없음(요인 분해) |

**왜 여러 장인가.** 결과를 여러 벌로 보이기 위해서가 아니라, 한 판의 결과만으로는 반론을 막을 수 없기 때문입니다.
- 주 결과판은 우리 엔진에 유리한 우연(미계측 배출구 · 유휴 비율 0.3 가정 · "큰 노드는 비효율" 편향)을 제거한 자리입니다.
- 반증판에서 우리 엔진이 이기면 판을 다시 설계해야 합니다.
- 계측 공백판은 주 결과판과 센서 유무만 달라, 두 판의 결과 차이가 곧 센서 공백의 크기이고 계측을 요구할 정량 근거입니다.
- 볼록·정격 어긋남·판정판 세 장은 엔진 가정이 틀렸을 때를 재는 자리입니다. 셋 다 주 결과판과 **노드 구성이 같아** 판 사이의 차이를 요인으로 읽을 수 있습니다(모집단이 다르면 그 읽기가 성립하지 않습니다). 앞의 두 판이 요인 하나씩을 귀속시키고 판정은 둘을 함께 건 판정판에서 합니다.
- 위상 독립 짝 2장은 옛 위상 식(`(seed·31^L + hash(nodeId)) mod 1000`)이 seed 를 늘려도 표본을 늘리지 못하던 결함을 닫은 판입니다. seed 별 결과는 서로 독립 복제이고 판 사이의 지점을 합쳐 세지 않습니다. n=3 으로는 검정하지 않고 중앙값 3값과 범위만 적습니다.
- 오목 판은 볼록 판 지수의 역수라는 대칭이 근거의 전부이며 물리적 근거는 없습니다. 생성 전력·역산 유휴·평가자 세 경로가 함께 바뀌므로 원인을 지목하지 않고, 결론의 적용 범위가 β<1 까지 뻗는지만 서술합니다.

판정판의 판정 셀은 현 시스템에 없는 전원 제어를 가정한 값이라 **배포 환경에서 재현되지 않습니다.**

## 4. 비교 전략

응답 열은 운영 엔진 → 엔진 변종 → 대조군 순서로 고정됩니다. 순서 목록과 구현의 집합이 어긋나면 열이 조용히 빠지는 대신 호출이 실패하도록 해 두었습니다.

| 구분 | id | 설명 | 비고 |
|---|---|---|---|
| 엔진 | `power` | `PowerAwareScheduler` | 운영 엔진 그대로 |
| 엔진 | `temperature` | `TemperatureAwareScheduler` | 운영 엔진 그대로 |
| 엔진 | `weighted` | `WeightedScoreScheduler` | 운영 엔진 그대로(기본 엔진) |
| 변종 | `resource-only-gated` | 자원전용(전력·온도 제약 유지) | 전력·온도·네트워크 가중치 0, 제약은 유지 |
| 변종 | `resource-only-ungated` | 자원전용(제약까지 해제) | 가중치 0 에 전력·온도 제약까지 해제 |
| 변종 | `weighted-affinity` | 가중 점수(링크 게이트 on · 링크 판에서만 weighted 와 다르다 · 판정 자격 없음) | `affinityEnabled=true` |
| 변종 | `power-s250` | 전력 인지(한계 전력 눈금 250W · 포화 발현 · 판정 자격 없음) | `marginalScaleWatts=250.0` |
| 변종 | `power-s1000` | 전력 인지(한계 전력 눈금 1000W · 무포화 · 판정 자격 없음) | `marginalScaleWatts=1000.0` |
| 변종 | `power-s0` | 전력 인지(한계 전력 눈금 0W · 정격 분모 · 구 방식 · 독립 증거 아님) | `marginalScaleWatts=0.0` |
| 변종 | `power-idle-fixed` | 전력 인지(유휴 역산 차단 · 대체값 고정 · 독립 증거 아님) | `idleFromMeasurement=false` |
| 변종 | `weighted-priority-age` | 가중 점수(스케줄 배치 순서: 우선순위 → 등록 순 · 기준 집합 밖 · 판정 자격 없음) | override 없음 · 순서 `ScheduleExecutionService.BY_PRIORITY_THEN_AGE` |
| 변종 | `weighted-priority-size` | 가중 점수(스케줄 배치 순서: 우선순위 → 크기 순 · 기준 집합 밖 · 판정 자격 없음) | override 없음 · 순서 `ScheduleExecutionService.BY_PRIORITY_THEN_SIZE` |
| 대조군 | `ffd-size` | 선착순(크기 내림차순) | |
| 대조군 | `ffd-priority-size` | 선착순(우선순위→크기) | |
| 대조군 | `pabfd` | 전력 인지 최적적합(엔진 전력식 공유 · ΔP 단독 · 깨우기항 없음) | 격차 지표의 분모 |
| 대조군 | `bfd` | 자원 최밀집(전력 무지) | |
| 대조군 | `coolest-first` | 최저 온도 우선(단순 규칙 · 재평가 없음) | 열을 점수에 넣는 유일한 대조군 |
| 대조군 | `random` | 무작위(고정 시드) | 시드 31개로 돌려 중앙값을 냄 |

- **자원전용 변종이 둘인 이유.** 전력·온도를 점수에서 뺀 것과 제약에서까지 뺀 것은 다른 질문입니다 — 앞은 "가중치를 안 봐도 제약이 막아 주는가", 뒤는 "제약까지 없으면 얼마나 나빠지는가". 섞으면 어느 쪽 효과인지 분리할 수 없습니다. 제약을 끈 변종은 막히는 자리가 없어 성공률이 정의상 최고이므로 경쟁자가 아니라 "제약이 없었다면 얼마나 배치됐을까" 를 보여 주는 천장입니다.
- **override 열.** 자원전용 2열은 정책 변종이라 기본 설정 열에 들고, 나머지 변종 5열은 노브 하나를 바꾼 override 열입니다. 바뀐 노브는 응답 `strategies[].engineConfigOverride` 에 실리고 설정 다이제스트에 들어갑니다.
- **스케줄 배치 순서 열.** 기본 엔진 `weighted` 를 스케줄 실행의 배치 순서 비교자 객체(`ScheduleExecutionService.BY_PRIORITY_THEN_AGE` · `BY_PRIORITY_THEN_SIZE`)로 정렬한 표본에 돌린 두 열입니다. 표본 순서로 돌리는 `weighted` 와 견주면 우선순위 정렬의 효과가, 두 열끼리 견주면 같은 우선순위 안의 크기 순 정렬 효과가 나옵니다. 하네스 워크로드는 생성 시각이 없어 마지막 기준이 동률이고, 정렬이 안정 정렬이라 표본 순서(도착 순서)가 등록 순 역할을 합니다. 순서는 엔진 노브가 아니어서 override 가 없고 설정 다이제스트 · 민감도 축에 넣지 않으며, 총량 짝 조건의 기준 집합에도 넣지 않습니다(7장). 두 분포 모두 HIGH 가 대형뿐이라 크기 순 효과는 NORMAL 안의 GPU 4코어 → 2코어 → 1코어 정렬에서 나오고 GPU 노드 경합이 섞입니다. 전력 엔진에는 순서 열이 없습니다.
- **독립 증거가 아닌 열.** `power-s0` 과 `power-idle-fixed` 는 이미 소비된 판정을 같은 자료로 재확인하는 열이라 라벨에 그 사실을 적습니다.
- **무작위 전략의 난수원.** `SplittableRandom` 을 씁니다. `java.util.Random` 은 작은 시드 1~31 의 첫 값이 한 값으로 뭉쳐 "시드 31개" 가 사실상 표본 1개가 되기 때문입니다.

## 5. 실행 조건

| 조건 | 값 | 이유 |
|---|---|---|
| 부하율 | 30 · 60 · 90 · 110 (%) | 30% 는 전 전략이 100% 성공해 표가 평평하고, 110%(수용 불가)가 없으면 성공률이 전략을 가르지 못합니다. 110% 셀은 건수 · 코어 두 성공률을 한 쌍으로 읽습니다(6장) |
| 부하율의 분모 | 정책 상한까지의 **여유** — `Σ max(0, min(cores × (정책 CPU 상한% − 실효 CPU%) / 100, memoryMb × (정책 메모리 상한% − 실효 메모리%) / 100 / 코어당메모리MB))`, 음수는 0 | 총 코어가 아닙니다. 노드마다 먼저 막히는 자원이 달라 두 축의 최솟값을 씁니다. 정의 문장이 응답에 그대로 실립니다 |
| 시각 지점 | 한 주기 12지점 | 시각을 하나로 고정하면 결정론적 전략은 셀마다 숫자가 하나뿐이라 분산이 0 이 됩니다. 지점마다 같은 스냅샷·같은 워크로드로 짝지어 차를 냅니다. 한 주기의 시각 지점이라 **독립 표본이 아닙니다** |
| 무작위 시드 | 1~31 | 시드 하나는 표본 1개입니다. 홀수라 중앙값이 잘 정의되고, 재현성은 "목록이 상수로 커밋되어 있다" 에서 옵니다 |

| 통전 판정 문턱 | CPU 5.0% | **비교의 회계 규칙**이지 엔진 노브가 아닙니다. 엔진 노브(`activeCpuPercent` 기본 5.0)와 같은 수를 따로 두는 이유는 운영 설정이 바뀌어도 같은 배치 결정의 회계가 달라지지 않게 하기 위해서입니다. 주 결과판에서 통전 집합이 불변인 구간은 3.0~5.0% 뿐이라 이 값을 바꾸려면 판을 다시 설계해야 합니다 |

| 오목 생성식 지수 | 0.625 | 1/1.6. 대칭이 근거의 전부입니다 |
| 정격 어긋남 비율 | ±10% | 어느 노드를 과대/과소로 둘지는 **손으로 고르지 않고** 층마다 한 양을 최소로 하는 분할로 정합니다(유휴 층은 깨우기 벌점 편향 ≤ 1%, 가동 층은 정격 합 편중 ≤ 5%). 손 배치는 연구자 자유도이고 그 자유도가 판정 결론을 만들기 때문입니다 |

| 워크로드 분포 | `heavytail`(기본) · `uniform` | 순위가 두 분포 사이에서 뒤집히면 그 사실 자체가 결과입니다. 판정 셀의 분포는 `heavytail` 로 고정(2026-09-15 소급 명문화) |

## 6. 지표

지표는 사전 등록된 15개이며 응답이 이 목록을 그대로 싣습니다. 지표마다 키·라벨·단위·좋은 방향·역할·유효 조건이 결과 코드보다 먼저 고정되어 있고, 유효 조건이 깨진 셀은 `valid=false` 로 나갑니다(조건 원문은 응답의 `validity`).

| key | 라벨 | 단위 | 방향 | 역할 |
|---|---|---|---|---|
| `placementRatePercent` | 배치 성공률 | % | `HIGHER_IS_BETTER` | `PRIMARY` |
| `generatorPowerW` | 총전력(생성식 기준) | W | `LOWER_IS_BETTER` | `PRIMARY` |
| `gapVsPabfdPercent` | 총전력 격차(전력 인지 최적적합 대비) | % | `LOWER_IS_BETTER` | `PRIMARY` — 판정 지표 |

- 방향 `CONTEXT_ONLY` 는 해석에만 쓰고 승패에 넣지 않습니다. 역할 `HONESTY` 는 "우리가 모르는 것" 을 드러내는 측정치라 판정이 아니라 숫자로 싣습니다. `SECONDARY` 는 참고용이며 헤드라인으로 쓰지 않습니다.
- **격차 지표.** `pabfd` 대비 총전력 격차는 **지점마다** 두 전략을 짝지어 낸 비의 중앙값이라, 두 전략의 총전력 중앙값을 나눈 수와 다릅니다. 식은 건수가 다르거나 `pabfd` 전력이 0 이하면 값 없음, 아니면 `(이 행 − pabfd) / pabfd × 100` 입니다. 이 식을 서비스가 아니라 규칙 클래스에 두는 이유는 식 자체를 사전 등록 대상으로 삼아 분모·부호·짝 조건을 단위 테스트가 잠그기 위해서입니다.
- **최고 온도가 없는 이유.** 배치 1건의 온도 상승분은 열관성 계수 × 코어 비율 × 기준 온도라 16코어 노드에 2코어를 얹으면 약 +1.4℃ 인데, 시각에 따른 자연 변동이 ±4.5℃ 로 배치 효과보다 3배 큽니다. 게다가 온도 제약이 "배치 후 예상 온도 > 임계" 를 막으므로 제약이 켜진 전략은 최고 온도가 전부 임계 이하로 잘려 한 비트짜리 열이 됩니다. 대신 경고 구간 노드 수·제약 개입 횟수·표준편차를 씁니다.
- **원격 MDC 배치 비율.** 워크로드에 데이터 MDC 를 배정한 판(링크 판)에서만 냅니다. 데이터 MDC 가 있는 성공 배치 가운데 노드의 MDC 가 데이터 MDC 와 다른 배치의 비율이고, 판 파일의 MDC 값으로만 셉니다 — 엔진의 링크 점수로 세면 링크 게이트를 켠 엔진이 자기 점수로 평가받습니다(2.1). 노드 MDC 가 없는 배치는 분모 · 분자에서 뺍니다. 데이터 MDC 를 배정하지 않은 판은 0 이 아니라 사유를 단 무효입니다. 링크 점수를 총점에 섞는 엔진은 `weighted` 하나라 효과는 `weighted` · `weighted-affinity` 쌍으로 읽고, 원격 배치는 자원·전력 제약 때문에 불가피할 수 있어 전력 판정과 섞지 않습니다. 관측값은 docs/13 8장에 있습니다.
- **자원 조각화 비율.** 배치를 마친 뒤 노드마다 기준 정책 상한까지 남은 여유 h(부하율 분모와 같은 식) 가운데, 워크로드 분포 파일에서 가장 큰 계층의 요구 코어 R(지금 두 분포 모두 4)을 하나 더 담지 못하는 자투리 h − R × ⌊h / R⌋ 가 여유 합에서 차지하는 비율입니다. R 코어 배치는 그 노드의 자투리를 바꾸지 않고 여유 합만 줄여 비율을 올리며, 자투리를 바꾸는 것은 R 보다 작은 배치입니다. 남은 4코어 자리 수 대신 비율로 낸 것은 여유 합이 다른 셀 사이에도 0~100 눈금에 놓이게 하기 위해서입니다. 다만 판 노드의 기존 사용률 때문에 배치 전 여유도 R 의 배수가 아니어서 배치 전에도 자투리가 있으므로, 값은 같은 셀 안의 열 사이 차이로 읽습니다. GPU · 전력 · 온도 제약은 보지 않습니다. 엔진 열과 그 변종은 표본 순서로 배치하고, 운영의 「크기 순」 배치 선택지 효과는 스케줄 배치 순서 두 열(4장)의 같은 지점 차로 읽습니다(아래 판독). 대조군 `ffd-size` · `ffd-priority-size` 쌍은 지금 두 분포가 4코어 계층 가운데 대형만 HIGH 라 두 정렬이 4코어 워크로드끼리의 순서만 달라, 크기 순의 조각화 효과를 가르지 못합니다. 관측값은 docs/13 8장에 있습니다.
- **코어 기준 배치 성공률.** 배치한 워크로드의 요구 코어 합을 그 시각 지점 표본의 요구 코어 합으로 나눈 비율이고, 배치 성공률과 같이 전 시각 지점에서 냅니다. 건수로 센 배치 성공률은 작은 워크로드를 많이 놓을수록, 이 값은 큰 워크로드를 놓을수록 높아집니다. 그래서 열마다 배치하지 못한 워크로드의 크기가 다르면 두 값의 순위가 갈립니다(`heavytail` 110% 셀에서는 건수 기준이 큰 것부터 놓는 다섯 열을 낮게 셉니다). 두 성공률은 한 쌍으로만 읽고 어느 쪽도 혼자 고부하 셀의 순위로 쓰지 않습니다. 제약을 끈 변종은 배치 성공률과 같은 이유(제약이 없을 때 얼마나 배치되는지 보여 주는 천장이라 비교하지 않음)로 무효입니다. GPU 요구는 세지 않고, 판의 워크로드는 메모리가 코어 수에 비례해 메모리로 센 값과 같습니다. 무작위 대조군의 값은 시각 지점마다 시드 31개 가운데 배치 건수로 고른 가운데 한 번의 값이라, 시드 31개의 코어 기준 중앙값이 아닙니다. 관측값은 docs/13 8장에 있습니다.
- **스케줄 배치 순서 열 판독(결과보다 먼저 정한 규칙).** 두 열의 조각난 여유 비율은 중앙값만이 아니라 같은 시각 지점의 차로 읽습니다 — 이 비율은 지점 사이 폭이 열 차이보다 커서 중앙값 차만으로는 주장할 수 없기 때문입니다. 판독 셀은 주 결과판의 짝 셀 다섯(`heavytail` 30 · 60 · 90% · `uniform` 30 · 60%)이고, 지점 집합 I 는 기준 집합 짝 지점 가운데 두 열의 건수가 기준 건수와 같은 지점입니다. 크기 효과 d 는 (크기 순 − 등록 순), 우선순위 효과 p 는 (등록 순 − `weighted`)이며 차의 절댓값이 0.0002 이하면 동률로 셉니다. |I| 가 6 미만이면 지점 부족으로 판독하지 않고, 음수가 I 의 과반이면 줄어든 쪽, 양수가 과반이면 늘어난 쪽, 그 밖은 갈림입니다. 중앙값끼리 견줄 때는 I 위의 중앙값을 씁니다. 110% 셀은 조각화가 무효라 두 성공률을 한 쌍으로 읽습니다. 12지점은 독립 복제가 아니라 검정하지 않고 판정 자격이 없습니다. 사전 추정과 반증 조건은 규칙 커밋 본문에 결과보다 먼저 적었고, 관측은 docs/13 8장에 있습니다.
- **전력 제약 개입 횟수.** 배치를 시도할 때마다 후보 노드 가운데 제외 까닭이 전력 계열(`ExclusionReason.isPower()` — 판에는 MDC 예산 · 워크로드 예산 · 실행 예산 입력이 없어 전력 여유 부족과 배치 후 예상 전력 초과 둘만 걸림)인 노드 수를 더한 값이고, 온도 제약 개입 횟수와 같이 시도당 계수라 전 시각 지점에서 냅니다. 앞 제약(자원 · CPU · 온도)에서 먼저 걸린 노드는 세지 않습니다. 엔진은 전력 제약을 실측 전력에 정격 × (1 − 유휴 비율 0.3) × 코어 비율을 더한 선형 증분으로 판단하므로(`PowerModel`), 판 노드의 실제 유휴비나 엔진에 알려 준 정격이 그 가정과 어긋나면 CPU 상한보다 먼저 전력 제약에 닿을 수 있습니다 — 이 지표는 그 두 가정(docs/15 4장의 유휴 비율 · 정격 두 행)이 판 노드와 어긋날 때 배치를 얼마나 막는지를 합성 판에서 보입니다(판 경로는 설정의 기본 정격 `defaultCapacityWatts` 를 읽지 않고 판 파일이 알려 준 정격을 씁니다). 결과보다 먼저 정한 판독 규칙은 이렇습니다. 배치 전부터 전력으로 막힌 노드는 열과 무관하게 시도마다 더해지므로 전략의 효과는 같은 셀의 열 사이 차이로만 읽고, 판 사이 차이는 셀의 프로브 사유와 함께 읽습니다. 중앙값과 최댓값을 함께 읽고(일부 지점에서만 개입하면 중앙값이 0), 판 사이 비교는 주 결과판과 노드 구성이 같은 판끼리 같은 열 · 같은 셀로만 합니다(반증판 제외). 값이 시도 수에 비례해 부하율 사이는 견주지 않습니다. 모든 열이 열 override 를 받지 않는 운영 설정 평가기로 판정하므로 눈금 · 역산 차단 열의 차이는 그 노브의 효과가 아니라 배치 위치의 차이입니다. 개입이 생성식 기준으로도 필요했는지는 가르지 못합니다. 전력 제약을 끈 변종은 항상 0 이라 사유를 단 무효입니다. 판정 자격이 없고, 사전 추정과 반증 조건은 규칙 커밋 본문에 결과보다 먼저 적었습니다. 관측은 docs/13 8장에 있습니다.
- **열 지표는 헤드라인이 아닙니다.** 열을 점수에 넣는 대조군이 `coolest-first` 하나뿐이라, 다른 대조군과의 차이는 알고리즘의 열 판단이 아니라 CPU 를 어디에 몰았는가의 부산물입니다.

## 7. 비교가 유효한 조건

**적게 배치하고 전력을 덜 쓰는 것은 승리가 아닙니다.** 총량 열(총전력 · 가동 노드 증감 · 경고 구간 노드 수 · 온도 표준편차)은 **기준 집합 전부의 배치 건수가 같은 시각 지점**에서만 비교하고, 다르면 `valid=false` 로 내리고 건당 값으로 비교합니다. 사유는 `전략 간 배치 건수 상이 (min~max건) — 총량 대신 건당 값으로 비교한다` 형식으로 셀에 실립니다.

**기준 집합.** override 없는 기본 설정 열 — 엔진 3 · 자원전용 2 · 대조군 6 입니다. 스케줄 배치 순서 2열은 override 가 없지만 기준 집합에 넣지 않습니다 — 넣으면 열을 더하는 것만으로 기존 열의 짝 지점이 바뀝니다. override 열과 스케줄 배치 순서 열은 그 마스크를 받아 자기 건수가 기준 집합의 건수와 같은 지점에서만 총량을 냅니다. 이렇게 고정한 이유는 짝 조건을 전 열로 잡으면 **열을 더하는 것만으로 기존 열의 값이 바뀌기** 때문입니다 — 배포 검증에서 변종 열 추가만으로 기존 열의 표본이 5 → 1 로 줄어든 것을 본 뒤의 사후 개정입니다(2026-09-14, docs/13 8장 규칙 이력). 기준 집합 밖 열이 총량을 내지 못한 지점이 있으면 전 지점 제외는 그 지표의 `invalidReason` 에, 일부 제외는 셀의 `totalsIncomparableReason` 에 적습니다(스케줄 배치 순서 열은 override 열 문장 뒤에 따로 적음) — 표본이 줄어든 사실이 응답에 보이지 않으면 이 규칙은 검증 불가입니다.

**자원 조각화 비율도 같은 짝 지점에서만 냅니다.** 총량은 아니지만 적게 배치한 열은 여유가 크게 남아, 같은 자리에서 견주면 조각화가 아니라 배치량을 재게 됩니다. 그래서 짝 지점이 없는 셀(주 결과판에서는 110% 두 분포와 90% `uniform`)은 사유를 단 무효이고, 그 셀은 건수 · 코어 두 배치 성공률을 한 쌍으로 읽습니다(6장). 다만 성공률에는 용량 부족과 전력 · 온도 제약으로 실패한 몫도 섞여 있어 조각화 몫만 가를 수는 없습니다. 짝 지점이라도 노드 여유 합이 0 인 지점은 값이 없습니다.

**격차 지표의 짝은 더 느슨합니다.** 이 행과 `pabfd` 둘만 보므로 표본 수가 총량 열 이상일 수 있습니다. `pabfd` 행 자신은 0 이 값이 아니라 기준이므로 무효입니다.

**미계측 격차.** 미계측 비율의 전략 간 격차가 10%p 를 넘으면 셀이 스스로 해석 문장을 붙입니다 — 전력·온도 순위가 알고리즘이 아니라 센서 공백을 반영할 수 있다는 뜻입니다. 이 임계로 판정을 저장하지는 않습니다. 임계가 바뀌면 이미 캡처된 자료가 어느 규칙으로 판정된 것인지 알 수 없게 되므로, 격차는 측정치로 싣고 임계는 해석 문장에만 씁니다.

건당 전력은 배치 0건이면 값이 없습니다. 원격 MDC 배치 비율도 데이터 MDC 가 있는 배치가 0건인 시각 지점은 값이 없고, 전 지점이 그러면 사유를 단 무효입니다(데이터 MDC 를 배정하지 않은 판은 판 단위 무효 · 6장).

## 8. 판정 규칙

판정은 **판정판의 한 셀**에서만 합니다. 셀을 결과를 보고 고르면 사후 선택이 되므로 결과보다 먼저 못 박았습니다. 기준선 값은 상수에 두지 않습니다 — 값은 판을 실행해야 나오고, 상수에 박으면 실행 순서가 커밋 순서를 강제하기 때문입니다.

| 항목 | 값 | 뜻 |
|---|---|---|
| 판정 셀 | `convex-misrated` · 부하율 60% · `AVAILABLE` · 분포 `heavytail` | 현 시스템에 없는 전원 제어를 가정하므로 판정 결과는 현 시스템에서 재현되지 않습니다 |
| 방향 판 | `main` | 판정은 한 곳에서만 하고(진실 원본이 둘이면 유리한 판을 고르는 자유도가 생깁니다), 주 결과판에서는 부호가 같은지만 봅니다 |
| 판정 값 | 판정 셀 `power` 행의 격차 지표 지점 배열 | 기준선 B 와 새 실행 N 을 같은 지점끼리 견줍니다 |
| 짝 지점 최소 개수 | 10(지점 12 이하) | 몇 곳 안 되면 중앙값이 한 지점의 이동으로 뒤집힙니다 |
| 중앙값 축소 문턱 | 2.0%p | 0 이면 부호만으로 성공이 되어 잡음이 결론이 됩니다 |
| 축소 지점 비율 | 10/12 이상 | 개수로 적으면 교집합이 하한과 같은 실행에서 적어 둔 것보다 센 기준이 됩니다 |
| 무시 폭 | 0.0002%p(4자리 눈금 두 칸) | 수학적으로는 같은 값인 변경이 부동소수 마지막 비트로 4자리 반올림 동점을 뒤집어 한 칸(0.0001) 움직이는 것이 관측된 뒤 예방으로 세운 잡음 하한입니다 |
| 다음 회차 판정 주어 | 공석(회차 4 소비 뒤) | 다음 지목은 결과 코드보다 앞선 `rules:` 커밋이 하나로 등록하며, 공석인 동안 판정 PR 은 열리지 않습니다(docs/13 8장 「판정 주어」) |

**절차.** 기준선 B 와 새 실행 N 에서 둘 다 값이 있는 지점의 집합 I 를 먼저 잡고,
1. **판정 가능** — |I| ≥ 10 이 아니면 판정 불가(성공도 실패도 아님). 한 판이라도 미달이면 전체를 성공으로 쓰지 않습니다.
2. **중앙값** — N 의 중앙값 ≤ B 의 중앙값 − 2.0, 두 중앙값은 **같은 집합 I** 위에서 냅니다. 지점별 차의 중앙값과 2항 미달까지의 최소 동률 지점 수를 함께 적되, 판정은 두 중앙값의 차로 합니다(추정량 교체는 결과를 본 뒤의 선택이 됩니다).
3. **지점** — B − N 이 무시 폭 이상인 지점이 ceil(10/12 × |I|) 이상. 축소는 부호 있는 값이 작아지는 것이며 절댓값이 아닙니다. 무시 폭 미만의 차는 동률입니다.
4. **방향 일치** — 주 결과판의 같은 셀에서 1항을 만족하고 중앙값 차가 무시 폭의 두 배(0.0004) 이상. 중앙값은 반올림이 한 번 더 겹쳐 최대 두 칸 잡음이 가능하므로 밴드는 두 칸을 넘어야 하고 여유 한 칸을 더해 네 칸으로 둡니다. 불일치면 **실패** — 판정판만 좋아진 결과는 판이 우리 엔진 쪽으로 기울었을 가능성을 배제하지 못합니다.

결말은 **판정 불가 · 성공 · 실패** 세 가지이고 실패해도 되돌리지 않고 게시합니다. 보고 절차(출처 대조 · 표 A~G · 결말 한 줄)와 판정 이력은 docs/13 8장이 맡습니다.

**판정 자격은 닫혀 있습니다.** 판정·방향 판정은 판정판과 주 결과판 두 판의 `power` 행에서만 성립하며, 그 밖의 판·열·지표는 전부 자격이 없습니다 — 판이나 열이 늘어도 이 문장은 바뀌지 않습니다.

**부수 보고(판정에 넣지 않습니다).**
- *민감도* — 판정 셀에서 `power`(눈금 500W) 대 `power-s250` 의 지점별 차 중앙값이 2.0 을 넘으면 격차 **수준**이 눈금에 의존한다고 읽습니다. 넘지 않으면 "영향의 증거를 못 찾음" 이지 영향이 없다는 주장이 아닙니다. 수준 의존이 곧 판정 의존은 아닙니다 — 판정량의 눈금 의존은 B·N 을 같은 눈금 열에서 각각 내어 견줘야 합니다. 눈금 250W 는 판정 시점 고정값 316W 아래라 포화가 발현하고, 1000W 는 무포화, 0W 는 정격 분모(구 방식)입니다.
- *위상* — 위상 독립 짝 판 2장의 seed 3 중앙값과 최소~최대 범위를 적습니다. 생략은 결격이고, 범위가 2.0%p 를 넘으면 단일 판 값이 그 폭 안의 한 점이라는 문장을 적습니다.
- *오목* — 오목 판의 같은 좌표 셀 중앙값(X), 선형 판 값(Y), 차(Z)와 부호, 역산 경로 기여(W)를 정해진 형식 그대로 적습니다. 원인을 지목하지 않습니다.
- *셀 밖* — 판정 자격 두 판의 전 셀 `power` 행 격차 중앙값을 기준선 파일과 대조해 악화·축소·동률·짝 집합 변화로 셉니다.

**실측 불변조건.** 판정 전제(눈금 S ≥ 316W)가 걸리는 값은 판정 시점에 고정한 316W 이고 규칙 축에 봉인되어 있습니다. 현재 등록 판 전부의 실측 최댓값(348.22W, 오목 판 bm-14 4코어)은 판 데이터의 사실이라 축 밖이며 판이 늘면 함께 갱신됩니다. 갱신값이 기본 눈금 500W 를 넘으면 포화가 기본 설정에서 발현한다는 뜻이므로 그 판의 도입을 보류합니다.

## 9. 규칙 관리 — 사전 등록 · 개정 · 기준선

**이 저장소가 주장할 수 있는 전부.** 판정 규칙 클래스(`BenchmarkRules`)는 2026-09-07 에 결과 코드보다 앞서 첫 선언됐고 이후 여러 차례 개정됐으며, 판정 상수(격차 문턱 · 지점 수 비율)는 비교 API 가 이미 실행 가능한 상태에서 등록됐습니다. 따라서 "결과를 볼 수 없는 상태에서 규칙을 정했다" 가 아니라 **"규칙 클래스가 결과 코드보다 먼저 존재했고 이후 개정은 전부 커밋 이력에 남아 있다"** 까지입니다. 이 클래스는 기술적으로 어디에 놓아도 컴파일되므로 커밋 순서가 유일한 증거이고, 계약 테스트가 상수들을 고정해 조용히 바뀌는 것을 막습니다.

**개정의 세 갈래**(docs/13 8장 규칙 이력 표의 라벨).

| 갈래 | 뜻 |
|---|---|
| 사전 등록 | 규칙 커밋이 결과·판 파일 커밋보다 앞 |
| 사후 개정 | 관측 수치를 본 뒤 고친 규칙. 개수는 세지 않고 목록으로 둡니다(세는 순간 낡는 숫자). 어느 경우에도 판정 셀·문턱·격차 정의·판정 자격은 바뀌지 않았습니다 |
| 규칙 보강 | 관측 수치가 개정 내용에 관여하지 않은 문장 보강 |

**규칙을 바꾸는 커밋.** 제목을 `rules:` 로 시작하고, 본문에 축·옛 값 → 새 값·사유를 적고, 결과 코드 변경을 같은 커밋에 담지 않습니다. 계약 테스트의 규칙 축 이력에 행을 더해야 테스트가 통과하므로 이력 누락은 기계가 막고, 커밋 순서는 리뷰가 봅니다.

**규칙 축 8 과 등급.** 규칙은 8개 축(지표 · 실행 격자 · 판 상수 · 판정 시점 실측값 · 민감도 · 판정 · 금지 조각 · 절차 문장)으로 나누어 축마다 다이제스트로 봉인합니다. 축을 나눈 이유는 "어느 규칙이 바뀌었나" 가 값 하나에 뭉개지지 않게 하기 위해서이고, 판정 보고의 출처 대조는 축마다 등급별로 읽습니다 — 전량 일치를 요구하면 절차 문장이 한 번만 고쳐져도 대조가 상시 발동해 무력화되기 때문입니다. 새 축은 등급을 정해야 생깁니다(세 집합의 합이 축 전체와 같음을 테스트가 봅니다).

| 등급 | 축 | 불일치 시 |
|---|---|---|
| 판정 무효화 | `judgment` · `sweep` · `boards` · `measured` | B 와 N 이 다른 규칙의 산출물 — 판정 불가 |
| 부수 보고 무효화 | `sensitivity` | 판정은 유효, 민감도 표만 판정 불가 |
| 표기 | `metrics` · `banned` · `prose` | 옛→새 값과 사유를 적고 진행 |

판정 주어는 `judgment` 축에 들어 있어, 판정을 게시하는 PR 안에서 지목을 바꾸면 기준선이 판정 불가가 되고 그 PR 은 기준선을 다시 뜨지 못합니다 — 지목 교체는 판정 없는 PR 의 재취득 경로입니다.

**기준선.** 기준선 B 는 두 셀의 지점 배열째(값 없는 자리 보존) 저장소 파일(`src/test/resources/scheduler/judgment/judgment-baseline.json`)에 두고, 상수·커밋 본문·중앙값만으로 대신하지 않습니다 — 중앙값만 남으면 3·4항은 영원히 재구성 불가입니다. 값은 **배포 jar 에 실리지 않습니다**(판정은 저장소 테스트의 일이고 배포 응답은 재현 참고입니다). 판정 PR 은 기준선 파일을 수정하지 않고(B 는 N 이전에 머지된 파일 — 리뷰 항목), 갱신은 보고 게시 뒤 별도 커밋으로 성패와 무관하게 직전 머지 리비전으로 합니다. 예외: 판정 무효화 축이나 판·워크로드 정의를 바꾸는 PR 은 기존 기준선이 이미 판정 불가이므로, 판정을 게시하지 않는 한 같은 PR 에서 다시 뜨고 이력 행에 사유와 옛 기준선과의 두 셀 중앙값 차를 적습니다. 재취득 이력은 docs/13 8장과 테스트의 기준선 이력이 진실입니다.

## 11. 한계

응답이 스스로 밝히는 한계 문장(`BenchmarkRules.LIMITATION`)을 그대로 옮깁니다. 계약 테스트가 "실측이 아니" · "생성식" · "한 대" 세 조각을 강제하므로 문장을 다시 써도 이 사실들은 빠질 수 없습니다.

> 이 비교의 전력·온도 값은 실측이 아니다 — 합성 클러스터 생성식의 출력이며, 그 계수(노드별 유휴 전력·정격·엔진에 알려 준 정격·생성식 지수·온도 계수 0.3)는 실데이터 없이 정한 가정이다. 평가자도 같은 생성식을 쓰므로 확인되는 것은 '엔진의 모델 가정과 생성식이 얼마나 다른가'이지 '생성식이 실제 서버와 같은가'가 아니다. 지수를 1 보다 크게 둔 판은 실서버 근사가 아니라 엔진 가정이 틀린 방향의 응력 시험이고, 문헌에는 반대 방향의 보고도 있다. 판 사이의 차이를 원인으로 읽으려면 그 판들이 주 결과판과 노드 구성이 같아야 한다. 전원 제어가 없는 현 시스템(UNAVAILABLE)에서 통합으로 아낄 전력은 정의상 0 이고, 아낄 수 있는 판(AVAILABLE)은 존재하지 않는 전원 제어를 가정한다. 온도 축의 대조군은 재평가 없는 최저 온도 우선 한 종뿐이고(다른 대조군은 열을 점수에 넣지 않으며, 온도 제약 C3 는 제약을 켠 전 전략이 똑같이 받는다 — 제약 해제 변종은 그 사실을 열마다 밝힌다), 기본 임계 75℃ 에서는 배치 후 예상 온도 제약이 시원한 노드에 작동하지 않아 그 전략은 초기 온도로 정렬한 통합에 가깝다 — 자원 최밀집(bfd) 열과의 차이가 곧 정렬 기준에 온도를 넣은 효과의 전부다. 따라서 열 지표는 헤드라인이 아니며, 이 API 는 전력 기반 배치·온도 제어의 효과를 결론 수준으로 증명하지 않는다. 배포 환경은 실존 노드가 한 대라 실환경 비교는 성립하지 않는다.

덧붙여:
- 지점 12개는 한 주기를 훑는 시각 지점이라 독립 표본이 아니고, 복제 축은 위상 독립 판의 seed 3 뿐입니다 — 어떤 검정도 하지 않습니다.
- 통전 문턱 5.0% 는 주 결과판의 불변 구간 3.0~5.0% 의 상단 경계에 붙어 있어 "엔진에서 독립했다" 거나 "민감도가 넓다" 고 말할 수 없습니다.
- 정격 어긋남 판의 부호 배치는 중립이 아닙니다 — 부호와 코어당 생성식 전력의 상관(유휴 층 약 −0.8, 가동 층 양)을 0 으로 만드는 분할이 이 노드 구성에 없어, 그 사실을 판 설명에 적고 갈라 읽습니다.
- 실데이터가 없어 생성식 계수의 타당성은 확인하지 못했습니다. 실장비 전력·온도가 수집되면 계수를 다시 정하고 판정 기준선을 재취득해야 합니다.
