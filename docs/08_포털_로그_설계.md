# 08. 포털 로그(PortalLog) 설계 — 관측 > 로그 관리

- 작성일: 2026-09-07
- 대상 화면: `/observability/log` (목록·상세), 향후 알람·작업 이력 연계
- 상태: 1~4·6·7단계 완료, 5단계(컨트롤러 부착)는 인증·계정·권한 묶음 완료, 나머지 묶음은 화면 확정 시. 갱신일: 2026-09-16

## 1. 목적과 범위

포털에서 일어난 일(사용자 조작, 인증, 인프라 작업, 알람 이벤트, 시스템 동작)을 **한 테이블 `portal_logs`에 `type`으로 구분해** 모으고, 관측 > 로그 관리 화면이 이를 조회한다.

기록 입구는 둘이다.

- **`@PortalLog` 애너테이션** — HTTP 요청 단위(컨트롤러 메서드)에 붙여 Aspect가 자동 기록. 사용자·IP·시각·성공/실패를 공통으로 채운다.
- **`PortalLogService.record(...)` 직접 호출** — 요청이 없는 곳(스케줄러, 알람 엔진, 인증 필터)에서 사용.

과제 산출물과의 관계 (Confluence 「2차년도 연구개발 목표」 WBS 기준):

- 포털 로그는 **WBS 4-1 자원 관리 포털 구현**(인증·권한·계정 관리)의 일부다. 포털 사용자의 행위를 남기는 감사 기능이며, 관측 > 로그 관리 화면이 그 조회 화면이다.
- **WBS 1-1 "분산 로그 수집 및 중앙 집중화 로깅 시스템 구축"**(완료, 김승한)은 Loki·Alloy(2026-09-28까지 Promtail) 파이프라인과 `LogController`(`/api/v1/monitoring/logs/**`)를 가리키며 이 설계와 별개다. 2026-06-04 인터페이스 검토 회의에서 세부3에 제공할 API 후보로 잡힌 `GET /logs/search?q&from&to`, `GET /logs/stream`(SSE)도 그 영역이다.

범위 밖:

- Loki 분산 로그(`LogController`), 자원 탐색기 서비스 로그(`/node/{nodeId}/services/**`)는 별도 도메인이다. 포털 로그는 포털 백엔드가 만든 사용자 행위·이벤트를 RDB에 구조화해 남기고, Loki 로그는 모니터링 대상 노드의 OS·프로세스가 찍은 텍스트를 Alloy가 수집해 Loki에 쌓는다. 생산자·저장소·규모·조회 모델·화면이 모두 달라 같은 테이블·API로 다루지 않는다. 접점은 두 가지로 한정된다: Loki 연동 장애를 `SYSTEM` 타입으로 기록하는 것, 향후 로그 알람(정책 종류 LOG)이 Loki를 평가해 발생하면 `ALARM` 타입으로 기록하는 것.
- 알람 발생 이력의 **원장**(`alarm_history`, 전송·확인)은 알람 도메인 테이블에 남는다. 포털 로그에는 요약 이벤트 행만 기록한다(§3.2).

## 2. 로그 타입

| type | 뜻 | 기록 주체 | 사용자/IP | 예시 (screen / action / content) |
|---|---|---|---|---|
| `AUTH` | 인증·세션·권한 | 인증 필터·핸들러 직접 호출 | 있음(실패 시 시도 ID) | 로그인 / 로그인 / `로그인 성공`, `로그인 실패: 비밀번호 불일치`, 로그아웃, 토큰 갱신, 비밀번호 변경, 권한 거부(403) |
| `AUDIT` | 포털 데이터·설정 변경(동기 CRUD) | `@PortalLog` | 있음 | 네트워크 구역 / 생성 / `네트워크 구역 생성: zone-a`, 알람 정책 / 수정 / `정책 수정: cpu-high`, 역할 / 자원 배정 |
| `ACTION` | 인프라에 실제 영향을 주는 작업. 진행중 상태 있음 | `@PortalLog(async=true)` 시작 + 완료 갱신 | 있음 | 가상머신 / 생성 / `Infra 배포: openstack-infra-01`, 노드 / 전원 제어, 에이전트 설치, 스케줄 수동 실행 |
| `ALARM` | 알람 발생·해소·확인 이벤트 | 알람 엔진·확인 API 직접 호출 | 발생·해소 없음, 확인은 있음 | 알람 / 발생 / `CPU Used > 80% 발생: node-01 (92%)`, 해소, 확인 |
| `SYSTEM` | 백엔드 내부 동작·외부 연동 상태 | 스케줄러·클라이언트 직접 호출 | 없음("시스템") | 수집 / 연동 실패 / `Tumblebug 429 rate limit (ns=openstack)`, Thanos 조회 지연, exporter 자동 등록, 배치 시작·종료 |
| `ACCESS` | 조회·열람 (프론트 화면이 호출하는 조회 API. 자동 갱신으로 반복되는 호출은 제외) | `@PortalLog(type=ACCESS)` | 있음 | 자원 탐색기 / 조회 / `전체 자원 트리 조회 (MDC: 전체, 키워드: web)`, 네트워크 구역 / 조회 / `네트워크 구역 조회: id 7`, 데이터 내보내기 |

AUDIT과 ACTION의 경계: AUDIT은 포털 DB 안에서 끝나는 즉시 완료 작업, ACTION은 Tumblebug·IPMI·에이전트 등 바깥에 명령이 나가 결과를 기다리는 작업. 프론트의 "진행중"과 완료 일시는 ACTION에서만 의미가 있다.

ACCESS 범위(2026-11-09 결정, 기존 "명시한 곳만" 원칙을 대체): **프론트 화면이 호출하는 조회 API 전부**에 붙인다. 단 두 가지는 제외한다.
- **자동 갱신 호출** — 자원 탐색기(트리 제외 전부)와 GPU 대시보드(본문·순위·추이)는 화면이 60초마다 같은 조회를 다시 부르므로, 붙이면 사용자 한 명이 화면을 켜 둔 것만으로 하루 수만 행이 쌓인다. 트리 4개(트리·루트·자식·검색)는 자동 갱신 밖이라 유지한다. 자동 갱신이 없는 화면(알람·IPAM·가상서버 그룹·토폴로지·랙·자산·사용자·역할·스케줄)은 사용자 동작당 1행이라 전부 남긴다.
- **로그 관리 화면 자체의 조회**(`PortalLogController`) — 로그 목록을 열 때마다 그 조회가 목록 맨 위에 쌓여 자기 기록으로 덮인다.

조회 행은 `action = "조회"`, 내용은 `"{대상} 조회: {식별자}"` 또는 목록이면 `"{대상} 목록 조회 (필터: …)"` 로 쓰고, 특정 자원을 열람한 행은 `ref_type`/`ref_id` 에 그 자원을 건다(§6). 조회 행이 변경 행보다 훨씬 많아지므로 ACCESS 보존 기간 분리는 운영 적재량을 보고 결정한다(§9).

## 3. 데이터 모델

### 3.1 `portal_logs`

엔티티는 `PortalLogEntry`(`monitoring/entity`)다. 애너테이션 `@PortalLog`와 이름이 겹치지 않게 접미어를 붙였다. 빌더(`PortalLogEntry.builder(type)…build()`)로만 만들고, 문자열은 컬럼 길이에 맞춰 잘라 저장하며 빈 `content`는 `-`로 채운다 — 로그가 본 요청을 실패시키지 않기 위한 규칙이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigserial PK | |
| `type` | varchar(16) | `AUTH` / `AUDIT` / `ACTION` / `ALARM` / `SYSTEM` / `ACCESS` |
| `started_at` | timestamptz NOT NULL | 요청 진입 또는 이벤트 시각. 화면의 "생성 일시" |
| `completed_at` | timestamptz | 응답 반환 또는 작업 완료 시각. IN_PROGRESS 면 null |
| `user_id` | varchar(64) | 로그인 ID. 시스템 이벤트는 null |
| `user_name` | varchar(100) | 표시명(기록 시점 스냅샷) |
| `client_ip` | varchar(45) | IPv6 대비 45 |
| `screen` | varchar(50) | 화면명(한글 표시명). 없으면 null → 화면에 "-" |
| `action` | varchar(30) | 작업(생성/수정/삭제/조회/로그인/발생 …) |
| `content` | varchar(500) NOT NULL | 내용 문구 |
| `result` | varchar(16) NOT NULL | `SUCCESS` / `FAILURE` / `IN_PROGRESS` |
| `description` | varchar(1000) | 실패 사유, 부가 설명 |
| `ref_type` | varchar(30) | 연관 원장 종류(`ALARM_HISTORY`, `INFRA_JOB` …) |
| `ref_id` | varchar(100) | 연관 원장 키 |
| `request_id` | varchar(64) | 요청 추적 ID(MDC). 서버 로그와 대조용 |
| `http_method` | varchar(8) | 요청 로그만 |
| `request_uri` | varchar(300) | 요청 로그만. 쿼리 스트링 제외 |
| `created_at` | timestamptz NOT NULL | 행 생성 시각(`@PrePersist`) |

인덱스: `(started_at)`, `(type, started_at)`, `(user_id, started_at)`, `(ref_type, ref_id)`. DDL: `deploy/sql/2026-09-07_portal_logs.sql`(운영 DB validate 모드라 수동 실행).

검색 대상 컬럼(프론트 계약과 동일, 5개): `user_name`, `screen`, `action`, `content`, `description`. `user_id`·`client_ip`는 검색 제외. 대소문자 무시 부분 일치이며 `%`·`_`는 리터럴로 이스케이프한다(`PortalLogSpecifications`).

### 3.2 알람과의 관계

알람 엔진은 `alarm_history`에 원장 행을 만들고, 같은 트랜잭션 커밋 후 `portal_logs`에 `type=ALARM, ref_type=ALARM_HISTORY, ref_id={historyId}` 요약 행 하나를 남긴다. 발생·해소·확인 각각 한 행이다. 로그 화면에서 알람 행을 클릭하면 `ref_id`로 알람 상세로 이동할 수 있다.

## 4. `@PortalLog` 애너테이션

위치: `com.innogrid.aims.common.log.PortalLog`. 구현 클래스는 `com.innogrid.aims.monitoring.log` 패키지에 둔다.

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface PortalLog {
    PortalLogType type() default PortalLogType.AUDIT;
    String screen();                 // 화면 표시명. 예: "네트워크 구역"
    String action();                 // 작업. 예: "생성"
    String content();                // SpEL 템플릿. 예: "'네트워크 구역 생성: ' + #request.name"
    boolean async() default false;   // true 면 반환 시 IN_PROGRESS 로 남기고 완료는 별도 갱신
    String refType() default "";
    String refId() default "";       // SpEL. 예: "#result.data.id"
    String userId() default "";      // SpEL. 인증 주체가 없는 요청(로그인·가입)에서 요청 인자로 사용자 지정. 예: "#request.email"
}
```

사용 예:

```java
@PortalLog(screen = "네트워크 구역", action = "생성", content = "'네트워크 구역 생성: ' + #request.name")
@PostMapping
public ApiResponse<NetworkZoneResponse> create(@Valid @RequestBody NetworkZoneRequest request) { ... }

@PortalLog(screen = "알람 정책", action = "삭제", content = "'정책 삭제: ' + #ids")
@DeleteMapping
public ApiResponse<Void> delete(@RequestParam List<Long> ids) { ... }

@PortalLog(type = PortalLogType.ACTION, async = true, screen = "가상머신", action = "생성",
           content = "'Infra 배포: ' + #request.infraName", refType = "INFRA_JOB", refId = "#result.data.jobId")
@PostMapping("/infra")
public ApiResponse<InfraJobResponse> deploy(@RequestBody InfraDeployRequest request) { ... }

@PortalLog(type = PortalLogType.AUTH, screen = "로그인", action = "로그인",
           content = "'로그인: ' + #request.email", userId = "#request.email")   // 인증 전이라 요청 이메일을 사용자로
@PostMapping("/login")
public ApiResponse<?> login(@RequestBody LoginRequest request) { ... }
```

SpEL 컨텍스트에 노출하는 변수:

| 변수 | 내용 |
|---|---|
| `#p0`/`#a0`, `#{파라미터명}` | 메서드 인자(`-parameters` 컴파일 옵션 필요, Spring Boot 기본 포함) |
| `#result` | 반환값(성공 시에만, 실패 시 null) |
| `#userId`, `#userName` | 인증 사용자 |

주의: 인증 사용자 변수가 인자 뒤에 들어가므로 **메서드 인자 이름이 `userId`·`userName`·`result` 면 그 변수에 가려진다.** 이런 인자는 위치 변수(`#p0`)로 참조한다(예: `UserController` 의 `@PathVariable Long userId` → `#p0`).

규칙: `content`는 **요청 인자 기준**으로 쓴다. `#result`는 실패 시 null 이라 내용이 비게 되므로 `refId`처럼 성공에만 필요한 곳에 쓴다. null 이 될 수 있는 인자는 엘비스로 대체 문구를 준다(`(#keyword ?: '-')`). 템플릿 평가가 실패해도 기록은 남긴다(content 에 `"식 원문 [평가 실패]"`).

평가 컨텍스트는 읽기 전용 `SimpleEvaluationContext`다(`PortalLogSpelEvaluator`). 빈 참조·`T()` 타입 참조·생성자 호출이 막혀 있어 템플릿이 코드 실행 통로가 되지 않는다. 컬렉션은 SpEL 변환 규칙대로 `1,2` 형태로 문자열화된다.

## 5. Aspect 동작

`PortalLogAspect`(`@Order(LOWEST_PRECEDENCE - 10)`, 트랜잭션 Aspect 바깥)가 `@annotation(portalLog)` 를 `@Around` 로 감싼다.

1. `PortalLogContextResolver.resolve()` 로 사용자·IP·요청 ID·HTTP 메서드·URI 를 읽고, 요청 속성에 "기록했음" 표시를 남긴다(§5.4 중복 방지).
2. `pjp.proceed()` — 예외가 나면 `content` 를 인자만으로 평가해 FAILURE + 메시지로 저장하고 예외를 그대로 다시 던진다. 응답 코드·메시지는 기존 예외 처리기가 결정한다.
3. 정상 반환이면 `content`(인자 + `#result`)를 평가하고, `refType` 이 있으면 `refId` 도 평가해 저장한다. `async=true` 면 IN_PROGRESS, 아니면 SUCCESS.
4. 저장은 `PortalLogWriter.write`(§5.3).

### 5.1 결과 판정

| 상황 | result | description |
|---|---|---|
| 정상 반환 | `SUCCESS` | null |
| 정상 반환 + `async=true` | `IN_PROGRESS` | null, `completed_at` null |
| `BusinessException` | `FAILURE` | 예외 메시지 |
| 그 외 예외 | `FAILURE` | 예외 클래스 단순명 + 메시지, 예 `IllegalStateException: db down` (스택은 서버 로그에만) |

### 5.2 공통 필드 채우기

| 필드 | 원천 |
|---|---|
| `user_id`, `user_name` | `SecurityContextHolder` 의 인증 주체 이름(= 로그인 이메일)이 `user_id`, `users.name` 이 `user_name`. 사용자 행이 없으면 `user_name` 도 ID 로 대체. 익명·미인증이면 둘 다 null |
| `client_ip` | `X-Forwarded-For` 첫 값 → `X-Real-IP` → `remoteAddr` |
| `request_id` | `RequestIdFilter` 가 MDC 에 넣은 값 — 클라이언트 `X-Request-Id` 재사용(영숫자·`._:-`, 64자 이내), 없으면 UUID. 응답 헤더 `X-Request-Id` 로도 내려간다 |
| `http_method`, `request_uri` | `RequestContextHolder` |
| `started_at` / `completed_at` | Aspect 진입 / 반환·예외 시각 |

### 5.3 기록 방식

- `PortalLogWriter.write`는 **`@Transactional(propagation = REQUIRES_NEW)`** 로 별도 트랜잭션에 저장한다. 본 업무가 롤백돼도 FAILURE 행은 남고, 로그 저장 실패는 본 요청에 영향을 주지 않는다(`catch` 후 `log.warn`). 저장 실패를 삼키는 책임은 Writer 에 있어 호출자는 예외를 신경 쓰지 않는다. `complete(refType, refId, result, description)` 도 같은 방식이다.
- 저장 방식(결정): 1차는 동기 REQUIRES_NEW. 요청 지연이 문제 되면 비동기 큐(테이블 큐 또는 `@Async`)로 전환한다. 전환 시 실패 기록 유실을 막기 위해 큐 적재는 동기, 발송(DB 저장)만 비동기로 한다.
- Aspect 순서는 `@Transactional` 프록시 **바깥**이어야 업무 트랜잭션 커밋 실패(예: 제약 위반 커밋 시점 예외)도 FAILURE 로 잡힌다.

### 5.4 메서드 진입 전 실패의 보조 경로

`@Valid` 검증 실패(400), JSON 파싱 실패, 필수 파라미터 누락, 타입 변환 실패는 컨트롤러 메서드가 호출되기 전에 예외가 나서 `@Around` 가 실행되지 않는다. 이를 남기는 것이 `PortalLogFallbackInterceptor`(`HandlerInterceptor`, `/api/**` 등록)다.

- `afterCompletion` 에서 핸들러에 `@PortalLog` 가 있고, Aspect 가 남긴 "기록했음" 요청 속성이 없고, 응답이 4xx/5xx 이면 FAILURE 행을 쓴다.
- 인자가 바인딩되지 않았으므로 `content` 는 SpEL 대신 `"{screen} {action} 요청 검증 실패"` 고정 문구, `description` 은 미해결 예외 메시지 또는 `HTTP {status}`.
- 응답 본문·상태는 바꾸지 않는다. 그래서 `@RestControllerAdvice`(전역·스케줄러 전용)와 충돌하지 않는다. 전역 `@ExceptionHandler` 를 추가하는 방식은 스케줄러 전용 예외 처리기와 응답 형식이 겹쳐 쓰지 않았다.

인증 실패(401)는 필터 단계라 여기서도 잡히지 않는다. `AUTH` 타입은 `PortalLogService.auth(...)` 로 인증 컨트롤러·핸들러에서 직접 남긴다.

## 6. 비요청 경로 — `PortalLogService`

요청이 없는 곳(스케줄러·알람 엔진)과 인증 주체가 아직 없는 곳(로그인 시도)은 `PortalLogService` 를 직접 호출한다. 저장 실패는 Writer 가 삼키므로 호출자는 예외를 신경 쓰지 않는다.

```java
portalLogService.system("수집", "연동 실패",
        "Tumblebug 429 rate limit (ns=" + nsId + ")", PortalLogResult.FAILURE, e.getMessage());

portalLogService.alarm("발생", criterion + " 발생: " + resourceName + " (" + observedValue + ")", historyId);
        // → ref_type=ALARM_HISTORY, ref_id={historyId}. 확인(ack)이면 현재 사용자가 함께 기록된다

portalLogService.auth(request.getEmail(), "로그인", "로그인 실패: 비밀번호 불일치",
        PortalLogResult.FAILURE, null);                       // 인증 주체가 없어 userId 를 직접 넘긴다

portalLogService.complete("INFRA_JOB", jobId, PortalLogResult.SUCCESS, null);   // ACTION 완료 갱신
portalLogService.record(PortalLogEntry.builder(PortalLogType.SYSTEM)…build());   // 임의 행
```

- SYSTEM 은 노이즈가 되기 쉬우므로 **상태 변화가 있을 때만** 기록한다(실패 시작·복구, 등록·해제). 매 주기 정상 동작은 기록하지 않는다.
  전이 판정은 `monitoring.log.IntegrationHealth`(화면 1개 = 인스턴스 1개, 장애 단위 키별 메모리 상태)가 맡고, 각 연동이 실패·성공을 관측할 때마다 `failed(key, what, cause)` / `recovered(key, what)` 를 부른다. 정상→실패에 `FAILURE`(원인), 실패→정상에 `SUCCESS`("… 복구") 각 1행, 반복 실패는 무기록. 상태는 메모리라 재기동 직후 첫 실패는 다시 기록된다(의도).
- ALARM 은 알람 엔진의 상태 전이(발생·해소)와 확인 API 에서 기록한다.

### 6.1 SYSTEM 기록 지점 (구현됨)

| screen | key | 관측 위치 | 장애로 보는 예외 | content 예 |
|---|---|---|---|---|
| `Thanos 연동` | `query` | `VictoriaMetricsClient.query/queryRange` (자원 탐색기·대시보드·스케줄러·알람 평가기 등 모든 PromQL 호출) | I/O(`ResourceAccessException`)·5xx·429. 그 외 4xx(잘못된 PromQL)는 호출자 문제라 제외 | `Thanos 조회 실패` / `Thanos 조회 복구` |
| `Tumblebug 연동` | `ns` | `TumblebugTreeBuilder.load` Namespace 목록(`GET /ns`, 재시도 뒤) | 모든 예외(= 트리의 `TUMBLEBUG_UNAVAILABLE` 상태와 1:1) | `Namespace 목록 조회 실패` |
| `Tumblebug 연동` | `infra:{nsId}` | 같은 곳, Namespace 별 `GET /ns/{ns}/infra` | 모든 예외 | `Infra 조회 (ns=openstack) 실패` |
| `알람 평가기` | `scope`, `metric:{코드}` | `AlarmEvaluationService` 역할 스코프·메트릭별 평가 | 모든 예외 | `Thanos 조회(CPU_USED_PERCENT) 실패` |

Thanos 가 내려가면 `Thanos 연동`(연결 자체)과 `알람 평가기 metric:…`(어느 메트릭 평가가 멈췄는지) 두 화면에 각 1행씩 남는다. 단위가 달라 중복으로 보지 않는다.

### 6.1 `ref_type` / `ref_id` 가 들어가는 경우

| 경우 | ref_type | ref_id | 용도 |
|---|---|---|---|
| ACTION `async=true` | 작업 종류(`INFRA_JOB` …) | 작업 키 | 완료 콜백이 IN_PROGRESS 행을 찾아 갱신(`findFirstByRefTypeAndRefIdAndResult`) — 필수 |
| ALARM 요약 행 | `ALARM_HISTORY` | 알람 이력 id | 로그 화면에서 알람 상세로 이동 |
| AUDIT 생성·삭제(선택) | 자원 종류(`ALARM_POLICY` …) | 생성/삭제된 자원 id | 이 로그가 만든/지운 자원 추적 |
| ACCESS 상세 조회(선택) | 자원 종류(`NETWORK_ZONE`, `SUBNET` …) | 열람한 자원 id | 누가 어느 자원을 열어봤는지 자원 기준으로 추적. 목록 조회는 null |

목록 조회(ACCESS)·인증(AUTH)·시스템(SYSTEM)처럼 가리킬 원장이 없는 행은 null 이다. `ref_type` 종류가 정해지면 enum 으로 전환한다.

## 7. ACTION 진행중 갱신

1. 요청 시 Aspect 가 `IN_PROGRESS` 행을 남기고 `ref_type/ref_id` 로 작업을 가리킨다.
2. 작업 완료를 확인하는 폴러·콜백(예: Tumblebug Infra 상태가 Running/Failed 로 바뀌는 시점)이 `portalLogService.complete(refType, refId, result, description)` 을 호출해 `completed_at`·`result` 를 갱신한다.
3. 일정 시간(예: 1시간) 넘게 IN_PROGRESS 면 `SYSTEM` 로그로 경고를 남기되 자동으로 FAILURE 로 바꾸지는 않는다.

1차 구현에서는 동기 API(AUDIT·AUTH)만 대상으로 하고, ACTION 은 VM 배포 기능이 생길 때 붙인다.

## 8. 조회 API

기존 `AuditLogController`(`/api/v1/monitoring/audit-logs`, 501 스텁)는 삭제하고 `PortalLogController` + `PortalLogQueryService`(읽기 전용 트랜잭션)로 교체했다.

| Method | Path | 파라미터 | 응답 |
|---|---|---|---|
| GET | `/api/v1/monitoring/portal-logs` | `type?`(다중), `keyword?`, `from?`, `to?`(날짜 `YYYY-MM-DD`, 양끝 포함, 한쪽만 지정 가능, 미지정 시 전체), `userId?`, `result?`, `page=1`, `size=10`(≤100), `sort=startedAt,desc` | `PageResponse<PortalLogListItemResponse>` |
| GET | `/api/v1/monitoring/portal-logs/{logId}` | | `PortalLogDetailResponse`, 없으면 404 |
| GET | `/api/v1/monitoring/portal-logs/export` | 목록과 동일 필터 | xlsx (후순위) |

`PortalLogListItemResponse`: `logId, type, startedAt, completedAt, userName, screen, action, content, result, description`
`PortalLogDetailResponse`: 목록 항목 + `userId, clientIp, refType, refId, requestId, httpMethod, requestUri`

정렬 허용 컬럼(`SortSupport`, 그 외는 400): `startedAt, completedAt, type, userName, screen, action, content, result, description`. 동률은 `id` 내림차순 2차 키로 고정한다. `from > to` 는 400.

프론트 계약과의 대응:

| 프론트 필드 | 응답 필드 | 비고 |
|---|---|---|
| `createdAtText`, `createdDate` | `startedAt`(ISO) | 포맷·날짜 파생은 프론트 |
| `completedAtText` | `completedAt` | null → "-" |
| `userDisplayName` / `userId` | `userName` / `userId` | 상세의 "관리자 (superadmin)" 조합은 프론트 |
| `accessIp` | `clientIp` | 상세 전용 |
| `result` `'success'\|'failure'\|'inProgress'` | `SUCCESS\|FAILURE\|IN_PROGRESS` | 대소문자 변환은 프론트(또는 `@JsonValue`) |
| 페이지 `pageIndex`(0-base) | `page`(1-base) | 프론트가 +1 |
| 기간 `YYYY-MM-DD` 양끝 포함 | `from/to` 날짜 | 서버가 `>= from 00:00`, `< to+1일 00:00`(KST)로 변환 |
| 정렬 `createdAt/completedAt/user/screen/action/content/result/description` | `startedAt/completedAt/userName/screen/action/content/result/description` | 이름 매핑 |

로그 화면의 타입 필터 UI 는 현행 유지(추가하지 않음)한다. `type` 파라미터는 API 에만 두어 자원 탐색기 알람 탭 등 다른 화면이 필요 시 쓴다. 조회 API 실패(메서드 진입 전 400)는 §5.4 보조 경로로 기록한다(결정).

## 9. 권한·보존

- 조회 권한(결정): 1차는 인증 사용자 전체. 이후 관리자만 전체 조회, 일반 사용자는 본인 `user_id` 행만 보는 옵션을 검토한다.
- 보존(결정·구현): 기본 1년, SYSTEM 타입은 90일. `PortalLogRetentionJob` 이 매일 03:30 에 `started_at < now - 보존일` 행을 지운다.
  - 설정 `aims.portal-log.retention.*` — `enabled`, `cron`, `default-days`(365), `system-days`(90), `batch-size`(5000), `max-batches-per-run`(200).
  - 배치 단위로 별도 트랜잭션(`TransactionTemplate`)이며, 네이티브 `DELETE … WHERE id IN (SELECT … ORDER BY started_at LIMIT n)` 으로 `(type, started_at)`·`(started_at)` 인덱스를 탄다.
  - 한 실행에서 배치 한도를 다 쓰면 멈추고 다음 실행에 넘긴다(첫 도입·장기 중단 뒤 적체 대비). 지운 행이 있으면 SYSTEM 행 1건("포털 로그 보존 / 정리 / … N건 삭제")으로 요약을 남기고, 실패는 `IntegrationHealth` 로 정상↔실패 전이에서만 남긴다.
  - 03:30 인 이유: 스케줄러 풀이 1개라 자정의 미터링 정리와 겹치지 않게 뺐다. 행 수가 커지면 월 파티션을 검토한다.
- 개인정보: `content`에 비밀번호·토큰이 들어가지 않도록 SpEL 템플릿 리뷰 규칙을 둔다. 요청 본문 전체를 자동으로 남기지 않는다.

### 10.1 컨트롤러 부착 계획

프론트 화면이 호출하는 컨트롤러를 도메인 묶음으로 나눠 붙인다. 묶음마다 같은 절차다: ① 엔드포인트별 `screen`·`action`·`content` 문구 확정(화면 = 프론트 메뉴명, 작업 = 생성/수정/삭제/실행, 조회는 "조회", 내용 = "{대상} {작업}: {식별 이름}"), ② 요청 DTO 필드로 SpEL 작성, ③ 대표 엔드포인트 성공·실패 MockMvc 테스트 1개, ④ 커밋 1개.

부착 기준(2026-11-09 결정, 2026-09-16 기준을 대체): **프론트(`aims-cloud-front`)가 실제 호출하는 엔드포인트는 변경·조회를 가리지 않고 전부** 붙인다. 프론트 호출은 `shared/api/index.ts` 의 `apiClient` 한 곳을 지나므로 `apiClient.get/post/put/patch/delete` 호출을 전수 조사해 백엔드 매핑과 대조했다(16개 base 경로, 변경계 43건·조회 약 150건). 같은 컨트롤러의 변경계는 프론트가 아직 안 불러도 함께 붙인다(예: 구역 인터페이스 저장). 제외는 §2 의 ACCESS 제외 두 가지(자동 갱신 호출 99개, 로그 관리 2개)와 검증·미리보기류(`/auth/validate`, `/services/validate`, `/cron/validate`, `/preview`, `/dry-run`), 서비스가 직접 기록하는 알람 확인, 프론트가 부르지 않는 컨트롤러(VM·클라우드 연결·카탈로그·이미지·태그·스토리지·에이전트·구 `IpController`/`NetworkController`·스케줄러 설정류)다.

IPAM·가상서버 그룹은 도메인 자체 이력(`NetworkAuditHistory`, `VmGroupActionHistory`)이 이미 있지만, 포털 로그는 전 화면 통합 조회가 목적이라 중복을 허용하고 `ref_type` 으로 도메인 이력과 잇는다.

| 순서 | 묶음 | 컨트롤러 | 타입 | 비고 |
|---|---|---|---|---|
