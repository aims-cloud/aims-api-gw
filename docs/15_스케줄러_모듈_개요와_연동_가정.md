## 요약

1. 스케줄러는 **판단 계층**입니다. 워크로드를 어느 노드에 둘지 결정하고 기록할 뿐, 실제로 올리는 일(실행 계층 · 1세부 API)은 `PlacementDispatcher` 경계 너머에 있습니다. 실행 API 가 정해지지 않아 지금은 기록형 구현체(`record` 모드)만 있습니다.
2. 메트릭은 수집하지 않고 저장소(Thanos/VictoriaMetrics)에서 당겨 씁니다. 저장소 대신 가상 클러스터를 쓰는 모의 모드는 기동 시 환경변수 `AIMS_SCHEDULER_MOCK_ENABLED` 로만 켜지고, `GET /api/v1/scheduler/metrics-source` 가 현재 메트릭 출처를 보여 줍니다.
3. 배치 엔진 3종(`weighted` · `power` · `temperature`)은 공통 부모 `AbstractScoringEngine` 위에서 노드별 점수 계산과 사유 문장만 다르게 구현합니다. 응답의 점수는 소수 넷째 자리 반올림(`Scores.round`)이며 이 식을 바꾸면 배치 응답 기준 파일 테스트가 깨집니다.
4. 실장비에 대한 가정 — 전력·온도는 IPMI 익스포터, GPU 는 DCGM 익스포터에서 오고, 익스포터마다 다른 `instance` 는 운영자 입력 원장 → 호스트명 일치 → 그대로 순으로 해석합니다. 정격 전력은 IPMI 로 알 수 없어 원장 또는 설정 기본값(500W)입니다.
5. 실데이터가 아직 없어 가정값으로 둔 계수(통전 문턱 5.0% · 열관성 0.15 · 유휴 비율 0.3 · 정격 500W · W 눈금 500 · 생성식 계수)와 판정 기준선은 실장비 값이 들어오면 다시 정해야 합니다(4장).
6. API 는 경로 59 · 작업 80(작업 = HTTP 메서드와 경로 한 쌍, docs/13 머리말의 「엔드포인트」)이며 6장 색인이 메서드·경로·docs/13 장을 나열합니다. 스키마 수는 적지 않습니다 — 필드의 진실은 Swagger 입니다.

## 2. 설계 결정

### 2.1 판단과 실행의 경계 — `PlacementDispatcher`

스케줄러는 배치를 **판단**하고 기록합니다. 워크로드를 노드에 실제로 올리는 것은 실행 계층(1세부 API)이고 그 API 는 아직 정해지지 않았으므로, `PlacementDispatcher` 인터페이스가 경계입니다.

- **모드와 폴백 순서** — 지금은 `RecordingPlacementDispatcher`(모드 `record`)가 외부를 부르지 않고 기록만 남기며 항상 수락(`ACCEPTED`)을 돌려주고, 워크로드는 `SCHEDULED` 에 머뭅니다. 실행 API 가 정해지면 원격 구현체를 추가하고 설정 `aims.scheduler.dispatch.mode` 로 고릅니다. `DispatcherRegistry` 는 설정 모드 → `record` → 첫 등록 구현체 순으로 넘어갑니다.
- **결과 규약** — 구현체는 예외를 던지지 않고 `Outcome`(ACCEPTED · REJECTED · UNAVAILABLE)으로 답하는 것이 원칙이며, `ACCEPTED` 만 진행하고 나머지는 워크로드를 `FAILED` 로 되돌립니다.
- **호출 시점과 예외** — 전달(디스패치)은 `PlacementService.place` 의 트랜잭션이 끝난 뒤 `PlacementDispatchService.afterPlacement` 에서 부릅니다. 디스패처가 예외를 던지면 `UNAVAILABLE` 로 기록하고 예외를 밖으로 내보내지 않습니다.
- **상태 흐름** — 왕복 기록은 `PlacementDispatch` 엔티티에 남습니다: REQUESTED → ACCEPTED/REJECTED/UNAVAILABLE, ACCEPTED → RUNNING/FAILED, RUNNING → COMPLETED/FAILED. `TIMED_OUT` 은 원격 모드용이라 `record` 모드에서는 도달하지 않습니다.

### 2.2 메트릭 출처 전환 — `SwitchingMetricsGateway`

메트릭 질의는 `SchedulerMetricsGateway` 하나를 통해서만 나갑니다. `SwitchingMetricsGateway` 가 설정 `aims.scheduler.mock-enabled`(기본 `false`)로 실제 저장소(`VictoriaMetricsGateway`)와 가상 클러스터(`SyntheticMetricsGateway`) 중 하나에 위임하며, 플래그는 **기동 시 한 번** 읽습니다 — 바꾸려면 환경변수 `AIMS_SCHEDULER_MOCK_ENABLED` 를 고치고 재시작합니다. 모의 모드가 켜지면 기동 로그에 WARN 을 남기고 `GET /api/v1/scheduler/metrics-source` 가 `synthetic` 을 보여 줍니다(조회 전용 · 출처를 바꾸는 API 는 없음). 가상 클러스터(`SyntheticCluster`, 기본 파일 `classpath:scheduler/synthetic-cluster.yml`)의 값은 시각의 결정적 함수라 같은 시각·같은 파일이면 언제 물어도 같고, `ipmi: false` 노드는 전력·온도 메트릭이 없어 실환경의 미계측 노드를 재현합니다.

### 2.3 엔진 공통 골격 — `AbstractScoringEngine`

세 엔진이 같이 쓰는 흐름(빈 후보 실패 → 노드마다 제외 판정 뒤 점수 계산 → 적격 후보 중 최고점 선택 → 점수 내림차순 정렬 → 후처리 → 선택 사유)은 `AbstractScoringEngine.schedule`(final)에 있고, 엔진은 부모의 추상 메서드 넷(`newRun` · `scoreNode` · `noEligibleReason` · `reason`)과 식별자(`getId` · `getName`)만 구현합니다(`afterRanking` 은 기본 빈 훅).

- **동점 처리** — 최고점은 엄격한 초과(`>`)로 고르므로 동점이면 입력 순서가 앞선 노드가 남습니다.
- **호출당 값** — 호출 한 번 동안만 써야 할 값은 호출마다 새로 만드는 `Run` 객체에 두고 엔진 인스턴스 필드에는 두지 않습니다. 엔진은 싱글턴 빈이라 호출 사이에 값이 섞이면 안 되기 때문입니다.
- **반올림과 계측 판정** — 점수 반올림은 `Scores.round`(소수 넷째 자리) 하나이며 상한·하한 자르기나 NaN 치환을 넣지 않습니다. 전력·온도를 쟀는지 가르는 조건은 `Measured` 에 모아 두었습니다. 다만 엔진마다 판정 식이 조금씩 달라 하나로 합치지 않았습니다 — 합치면 응답이 바뀝니다(5장).

| 엔진 id | 클래스 | 비고 |
|---|---|---|
| `weighted` | `WeightedScoreScheduler` | 기본 엔진(`EngineRegistry.DEFAULT_ENGINE_ID`). 엔진을 생략하면 적용 정책의 기본 엔진(`defaultEngine`)을 쓰고, 그것도 없으면 이 엔진을 씁니다(docs/13 5장). 모르는 id 는 API 가 400 으로 거부합니다 |
| `power` | `PowerAwareScheduler` | 전용 `PowerRun`. 정렬 뒤 통합 여유 후처리 |
| `temperature` | `TemperatureAwareScheduler` | 전용 `TempRun` |

### 2.4 그 밖의 결정(한 줄씩)

- **응답 형태의 주인은 `dto` record** — 엔티티를 직접 직렬화하지 않습니다(`NodeResponse` 가 그 예). 예외는 1장 표의 세 응답뿐입니다.
- **트랜잭션 범위** — `SchedulingService` 는 메트릭 조회를 트랜잭션 밖에서 하고, `PlacementService` 는 메트릭 조회 없이 엔진 판단과 DB 저장만 트랜잭션 안에서 합니다. 일괄 재개·상태 전이·예약 취소는 `SchedulingService` 의 공개 메서드가 트랜잭션을 열고, 본문(`WorkloadStatusChanger`)과 전달 기록 마감이 그 안에서 돕니다. 스케줄 실행의 배치 저장은 같은 트랜잭션에서 워크로드 상태가 아직 `PENDING`·`FAILED` 일 때만 결정한 상태로 옮기는 조건부 갱신을 먼저 해, 겹친 다른 실행·단건 배치가 그 사이 커밋한 배치를 덮지 않습니다.
- **한 실행 한 번 수집** — `PlacementContext` 가 노드 상태를 한 번 모아 공유하고 예약분을 차감합니다.
- **대조군은 빈이 아님** — 비교 전용 전략(`PlacementStrategy`)은 `SchedulingEngine` 을 구현하지 않아 운영 경로에서 실행될 수 없습니다.
- **설정은 한 클래스** — `SchedulerProperties`(접두사 `aims.scheduler`)가 기본값을 들고, 운영은 환경변수로만 덮어씁니다.
- **포털 로그는 가져다 씀** — 스케줄 화면 작업 8개는 `common.log.PortalLog` 애너테이션으로 기록하고(docs/13 2장 「포털 로그 기록」), 자동 실행 실패 · 복구는 `ScheduleRunner` 가 포털 로그 모듈의 `IntegrationHealth` 로, 기동 회수 요약은 `PortalLogService.system` 으로 SYSTEM 행을 남깁니다(같은 장 「자동 실행 실패 · 복구(SYSTEM)」). 기록 · 저장은 포털 로그 모듈(`monitoring/log`)이 맡고, 스케줄러는 그 코드를 고치지 않습니다.
- **핵심 메트릭이 없는 노드는 후보에서 제외** — CPU 사용률·코어 수·MemTotal·MemAvailable 중 하나라도 모르면 0 으로 채우지 않고 WARN 로그와 함께 뺍니다(`NodeResourceCollector`). 디스크·네트워크·전력·온도는 부가 메트릭이라 없으면 0 입니다.

## 3. 1세부 연동 가정

### 3.1 실행 계층(배치 실행 API)

`PlacementDispatcher` 설명에 적힌, 원격 구현체가 지켜야 할 계약입니다. 1세부 실행 API 가 이와 다르게 정해지면 구현체와 이 표를 함께 고칩니다.

| # | 가정 | 근거 |
|---|---|---|
| 1 | 실행 요청은 비동기로 수락되고 즉시 식별자(`externalRef`)를 돌려줌 | `PlacementDispatcher` 설명 |
| 2 | 진행 결과(RUNNING · COMPLETED · FAILED)는 우리 콜백 `POST /api/v1/scheduler/dispatches/{dispatchId}/result` 로 옴 | 같음 · `PlacementDispatchController` |
| 3 | 식별은 우리 dispatch id 로 함. 멱등키(`workloadId:scheduledAt` 밀리초)는 우리가 실행 요청에 넣어 보내는 값이며 콜백은 이 키를 받지 않음 | `PlacementDispatcher.Request` · `PlacementDispatch` |
| 4 | 콜백은 JWT 인증만 요구하고 역할 제한은 없음. 실행 계층용 서비스 계정은 운영에서 발급(미정) | `SecurityConfig` · 스케줄러 패키지에 `@PreAuthorize` 없음 |
| 5 | 취소(`cancel`)는 호출자의 DB 트랜잭션 안에서 불리므로 원격 호출은 커밋 뒤로 미뤄야 함 | `PlacementDispatcher.cancel` 설명 |
| 6 | 원격 모드용 `aims.scheduler.dispatch.timeout-minutes`(기본 30)는 아직 읽는 코드가 없음 | `SchedulerProperties.Dispatch` |
| 7 | RUNNING 콜백은 워크로드가 노드 자원을 쓰기 시작할 때 옴. 받은 시각을 워크로드의 시작 시각으로 써서 CPU·메모리·디스크 예약을 그때부터 메트릭 지연(기본 10분) 동안 남김. 콜백이 실제 시작보다 늦으면 그만큼 예약이 더 남고, 이르면 사용률에 잡히기 전에 예약이 빠질 수 있음. 콜백 없이 운영자 상태 변경으로 시작한 워크로드는 배치 시각으로 대신함 | `PlacementDispatchService.runningSince` · `PlacementContextAssembler` 예약 반영(`SchedulingService.createContext` 가 부름) |

콜백 본문은 `DispatchResultRequest` — `status`(RUNNING · COMPLETED · FAILED), `externalRef`(최대 200자), `message`(최대 500자, 선택)입니다. 같은 상태를 다시 보고하면 200 에 변경 없음, 상태 흐름(2.1) 밖의 전이는 409, 없는 id 는 404, 잘못된 `status` 나 길이 초과는 400 입니다. 필드의 뜻은 docs/13 7장에 있습니다.

## 5. 결정 대기 동작

배치 응답 기준 파일 테스트(`PlacementResponseGoldenTest`)는 아래 세 동작을 지금 출력 그대로 고정해 두었습니다. 바꿀지는 따로 정합니다. 동작을 바꾸는 변경은 별도 PR 로 하고 같은 커밋에서 해당 기준 파일을 갱신합니다.

| # | 현재 동작 | 기준 파일 | 기록된 값 |
|---|---|---|---|
| 1 | 가중치 엔진이 전력은 있고 정격이 0 인 노드에 전력 여유 만점을 줍니다 | `weighted-mixed-nodes.json` | `전력여유 1.0` · `powerScore 1.0`(선택 노드) |
| 2 | 전력 엔진이 미계측 선택 노드의 사유에 전력·열 중립값 숫자를 그대로 적습니다 | `power-unmeasured-winner.json` | 사유 `(전력:0.50 열:0.50)` |
| 3 | 온도 엔진의 냉각 점수가 음수가 될 수 있습니다(배치 후 예상 온도가 임계를 넘는 노드) | `temperature-mixed-nodes.json` · `temperature-unmeasured-winner.json` | `냉각점수 -0.1378` |

기준 파일로 고정되지 않은 보류 동작 하나: `PowerAwareScheduler` 의 설정 인자 생성자(테스트 전용)는 `NetworkModel` 을 기본 설정으로 만들어 넘겨받은 `aims.scheduler.network.*` 4개 키(`latency-scale-ms` · `degraded-penalty` · `link-weight` · `unknown-link-score`)를 쓰지 않습니다. 운영 경로(스프링 생성자)는 `NetworkModel` 빈을 주입받아 영향이 없고, 전력 엔진이 그 모델에서 부르는 `localTrafficScore` 는 이 키들을 읽지 않으므로 출력 차이도 없습니다 — 정리 대상이지 결함은 아닙니다.

## 6. API 요약과 색인

스케줄러 API 는 경로 59 · 작업 80 입니다(컨트롤러 매핑에서 뽑은 목록이 Swagger `/v3/api-docs` 와 같음). 필드·오류·변경 이력은 docs/13 이 맡고 여기서는 **어느 컨트롤러가 어느 경로 묶음을 담당하는지**만 적습니다. 스키마 수는 적지 않습니다 — 요청·응답 필드가 바뀌어도 이 표는 바뀌지 않게 하기 위해서입니다.

1. 워크로드 등록 `POST /workloads`

4. 결과 `GET /history/page` · `GET /schedules/{id}/runs/{runId}`
5. 전달 기록 `GET /workloads/{workloadId}/dispatches`
6. 실행 계층 콜백 `POST /dispatches/{dispatchId}/result`

- 4장의 가정값이 바뀌는 PR(설정 기본값·생성식 계수·판정 기준선)은 같은 PR 에서 4장 행을 갱신합니다. 판정 기준선 다이제스트는 이 문서 4장 · docs/14 12.2 · docs/13 8장 세 곳에 있으니 함께 고칩니다.
