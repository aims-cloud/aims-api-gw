# 09. 알람 설계 — 관측 > 알람 (발생 이력 · 정책)

- 작성일: 2026-09-07
- 대상 화면: `/observability/alarm` (발생 이력 탭, 정책 탭, 정책 상세·마법사)
- 상태: 설계안 (코드 반영 전). 현재 백엔드는 `AlarmHistoryController`·`AlarmPolicyController` 15개 엔드포인트가 인터페이스만 있고 서비스는 전부 501, 구 `AlarmController`·`AlarmEvaluationService`(메트릭 4종 하드코딩)만 동작한다.
- 구성: **A부** 평가·전송 엔진 선정(Thanos Ruler+Alertmanager vs 백엔드 자체) → **B부** Confluence(AIMS 하위) 대조 및 재설계 → **C부** 기존 초안(feat/event-alarm: AlarmRule·AlarmHistory·Event·AlarmEvaluationService) 계승 규칙. B·C부가 최종안이며 A부와 충돌하는 곳은 B·C부를 따른다.
- 관련 문서: docs/06 자원 탐색기 트리 설계(자원 스코프·PromQL 표준식 재사용), docs/08 포털 로그 설계(§3.2 ALARM 타입 기록)

## 요약

1. **백엔드 자체 평가·전송**(`@Scheduled` + ShedLock, 메트릭 단위 묶음 평가)으로 구현한다. Alertmanager는 도입하지 않는다 — 화면이 요구하는 수신자별 전송 결과·확인·조직 수신자·본문 저장이 Alertmanager 모델 밖이라 결국 백엔드가 발송해야 하고, 도입 시 컨테이너 2개와 설정 재생성·리로드 결합만 늘어난다.
2. Confluence 기술 조사가 권고한 가치는 **기능으로 흡수**한다: 억제(사이트 다운 시 하위 알람 전송 차단), 내장 시스템 규칙(에이전트 다운·사이트 생존성·데드맨·연동 장애·GPU 스로틀), WEBHOOK 채널·구독 API·`GET /events`(세부3), 알람 → 조치 이벤트 훅(온도 2단계는 스케줄러).
3. 표준 스택과의 접점은 **Alertmanager v2 호환 수신 엔드포인트**(`POST /api/v2/alerts`)다. 세부1·3·KETI가 자기 Alertmanager로 평가한 알림을 보내면 같은 원장에 합류한다.
4. 알람 원장(`alarm_history`)은 알람 도메인에 두고, 포털 로그에는 `ALARM` 타입 요약 행만 남긴다.
5. 기존 초안(feat/event-alarm)의 방향은 그대로 잇는다: 백엔드 주기 평가, `mdc_id`·`instance` 라벨 조인, `events` 원장을 통한 이벤트 노출(`GET /api/v1/monitoring/events`), 이력 상태 OPEN→ACKNOWLEDGED→RESOLVED. 바뀌는 것은 규칙을 정책 원장으로 확장하고 메트릭 하드코딩을 카탈로그로 바꾸는 것이다(C부).
6. 성능: 정책 수가 아니라 자원(시계열) 수가 비용을 정한다. 메트릭 종류별 벡터 한 번 조회 후 메모리 대조라 정책 수천 개까지 무관하다(A.3.2 보강, B.5).

## A부. 평가·전송 엔진 선정 분석

### A.1 배경

- 현재 백엔드에는 `AlarmEvaluationService`가 1분 주기(`@Scheduled`)로 `alarm_rules`를 순회하며 Thanos Query에 즉시 쿼리를 던져 임계 초과 시 `alarm_history`에 행을 적재한다. 메트릭 4종 하드코딩, 지속시간·중복 억제·해소 없음, 알림 발송 없음.
- 프론트 알람 화면(`/observability/alarm`)이 요구하는 기능은 단순 임계 알림을 넘어 **정책 원장·전송 원장·확인 처리**를 포함한다.
- Thanos 스택(receive/query/store/compactor)과 Prometheus(remote_write)는 이미 테스트베드에 있다. **Thanos Ruler와 Alertmanager는 없다.**

#### A.1.1 화면이 요구하는 기능 (프론트 코드 기준)

| 구분 | 요구 기능 |
|---|---|
| 정책 | 정책명, 역할, 배포영역, 대상 자원 유형(node/vm/gpu), 대상 범위(전체/개별 + 대상 자원 목록), 메트릭 유형/메트릭, 임계값, 연산자, 알람 레벨(info/warning/critical), 설명, 수신자(개인/조직), 채널(Email/SMS), 조건 지속 시간(현재 "즉시" 고정), 생성/편집/복제/삭제, 미리보기 시계열 |
| 발생 이력 | 발생 일시, 레벨, 자원 유형/이름, 기준 문자열(`CPU Used > 80%`), 관측값, 역할, 배포영역, 정책명, **알림 전송 건수**, 확인 상태 |
| 전송 이력 | 대상(개인/조직)별 채널별 결과. 개인은 단일 상태(성공/전송중/실패), 조직은 성공/전송중/실패 **카운트** |
| 메시지 상세 | 제목, 발송 시점 치환된 본문, **수신자별** 이름/ID/수신 주소/결과/전송 일시/실패 사유 |
| 확인 | 확인 내용 입력 → 확인자·확인 시각 저장, 확인 내역 조회 |
| 스코프 | 역할(role_namespaces/role_assets)과 배포영역으로 정책·이력 필터 |

핵심은 **수신자 단위 전송 결과와 확인 처리가 1급 데이터**라는 점이다. 이것이 엔진 선택을 좌우한다.

### A.2 후보 아키텍처

#### A안. Thanos Ruler + Alertmanager (Prometheus 표준 방식)

```
정책 저장(DB) → 백엔드가 rule YAML 생성 → Thanos Ruler (PromQL 평가, for 지속시간)
   → Alertmanager (그룹핑·중복제거·억제·무음, 라우팅) → 수신기(Email SMTP / Webhook)
   → 이력 저장을 위해 Webhook 수신기로 백엔드가 다시 받아 DB 적재
```

- 추가 컴포넌트 2개: `thanos-rule`, `alertmanager` (+ 각 설정 파일의 동적 생성·리로드).
- 정책 변경마다 rule YAML과 alertmanager.yml(라우트·수신기)을 재생성하고 `/-/reload` 호출.

#### B안. 백엔드 자체 평가·전송 (현행 구조 확장)

```
정책 저장(DB) → 스케줄러(@Scheduled + ShedLock)가 정책별 PromQL 생성 → Thanos Query 즉시 쿼리
   → 상태 머신(정상 → 대기(for) → 발생 → 해소), 중복 억제
   → 알람 발생 행 적재 → 전송 작업 생성 → 발송기(Email/SMS) → 수신자별 결과 적재 → 확인 처리
```

- 추가 컴포넌트 없음(SMTP 서버·SMS 게이트웨이는 어느 안이든 필요).
- 기존 `AlarmEvaluationService`를 정책 원장 기반으로 교체하는 연속선상의 작업.

#### C안. Thanos Ruler 평가 + 백엔드 수신·전송 (절충)

```
정책 저장(DB) → rule YAML 생성 → Thanos Ruler → (Alertmanager API v2 호환 엔드포인트를 백엔드가 구현)
   → 백엔드가 알람 수신 → 이력·전송·확인은 B안과 동일
```

- Alertmanager 없이 Ruler만 추가. Ruler는 `--alertmanagers.url`에 Alertmanager API(`POST /api/v2/alerts`)를 구현한 어떤 서버든 지정 가능하므로 백엔드가 그 역할을 맡는다.
- 평가(for 지속시간, ALERTS 시계열, 재시작 복원)는 Ruler에 위임, 나머지는 백엔드.

#### A.3.1 A안이 막히는 지점

프론트 화면의 전송 이력·메시지 상세·확인 기능은 **Alertmanager 모델 밖**이다. Alertmanager는 "알림을 어디로 보낼지"까지만 책임지고, 누구에게 성공했는지·본문이 무엇이었는지·누가 확인했는지는 남기지 않는다. 결국 Alertmanager의 Email 수신기를 쓰지 못하고 Webhook으로 백엔드에 넘겨 백엔드가 수신자를 풀고 발송하고 기록해야 한다. 그러면 Alertmanager가 하는 일은 그룹핑·중복 제거만 남는데, 그 대가로 컨테이너 1개와 정책 변경마다 YAML 재생성·리로드가 붙는다.

또 조직(팀) 수신자는 구성원이 바뀌면 수신기 정의가 바뀌어야 하므로, 사용자 관리 이벤트가 Alertmanager 설정 재생성으로 이어진다. 결합이 늘어난다.

#### A.3.2 B안의 약점과 대응

| 약점 | 대응 |
|---|---|
| 정책 수가 늘면 즉시 쿼리 수가 늘어난다 | 평가 단위를 정책이 아니라 **(메트릭, 주기)** 로 잡는다. 메트릭 종류(카탈로그 6~10개)별로 전체 자원 벡터를 한 번 조회하고 메모리에서 정책별 대상·임계값에 대조한다. 주기당 쿼리 수 = 메트릭 종류 수로 정책 수와 무관. 비용은 자원(시계열) 수가 정하며 이 규모(호스트 수백·VM 수십)에서는 정책 수천 개까지 문제 없음. 상태 행은 전이가 있을 때만 쓰고, 알람 평가용 Thanos 요청은 별도 타임아웃·동시 실행 상한을 둔다 |
| 다중 인스턴스에서 중복 평가 | ShedLock(DB 락)으로 평가 작업 단일 실행 |
| 재시작 시 pending(for) 상태 유실 | 정책×자원별 상태 행(`alarm_states`)을 DB에 두고 재시작 후 이어감 |
| 평가 코드 품질이 곧 알람 신뢰성 | 상태 머신을 순수 함수로 분리해 단위 테스트로 굳힘. 현재 자원 탐색기 PromQL 표준식·`MetricSelector`를 그대로 재사용 |

#### A.3.3 Spring Batch에 대해

Spring Batch는 대용량 데이터를 chunk 단위로 읽고·처리하고·쓰며 실패 지점부터 재시작하는 **배치 작업 프레임워크**다. 알람 평가는 "짧은 주기로 소량의 쿼리를 반복 실행하고 상태를 갱신"하는 작업이라 Job/Step/Chunk 모델이 맞지 않고, 메타 테이블 9개(BATCH_JOB_INSTANCE 등)만 늘어난다. 이 용도의 표준 조합은 `@Scheduled`(또는 Quartz) + ShedLock이다. 이미 `AlarmEvaluationService`, `PrometheusTargetService`, `ResourceCollectorService`가 같은 방식이다. Spring Batch가 어울리는 자리는 나중에 생길 수 있는 "발생 이력 월별 아카이빙·집계" 정도다.

### A.4 판단

**B안(백엔드 자체 평가·전송)을 채택한다.**

근거:

1. 화면이 요구하는 전송 원장·확인·조직 수신자 처리는 어느 안을 택해도 백엔드가 구현해야 하고, 이것이 전체 작업량의 대부분이다. Alertmanager를 붙여도 줄어드는 것은 "for 지속시간과 중복 제거" 정도다.
2. Alertmanager 도입은 컨테이너 2개(Ruler, Alertmanager), 설정 파일 동적 생성·리로드 경로, Webhook 수신기, 사용자 변경 → 설정 재생성 결합을 추가한다. 시제품 단계에서 장애 지점을 늘릴 이유가 없다.
3. 기존 코드가 이미 B안 구조(`@Scheduled` 평가 + Thanos Query)로 되어 있어 연속적으로 확장할 수 있고, 자원 탐색기에서 만든 PromQL 표준식·라벨 선택자·역할 스코프를 그대로 재사용한다.
4. 공인시험·정량 평가 시 "알람 발생 → 전송 → 확인"의 전 과정을 백엔드 한 곳에서 추적·재현할 수 있다.

단, **평가부를 `AlarmEvaluator` 인터페이스로 분리**해 두어 다음 조건이 오면 C안(Thanos Ruler가 평가, 백엔드가 Alertmanager API 호환 엔드포인트로 수신)으로 갈아탈 수 있게 한다.

- 정책 수가 수천 단위로 늘어 즉시 쿼리 부하가 문제 될 때
- Grafana에서 ALERTS 지표를 함께 보여야 할 때
- 다른 팀(모니터링 담당)이 Prometheus rule 문법으로 정책을 직접 관리하기를 원할 때

C안으로 가더라도 전송·이력·확인 모듈은 그대로 쓰고, 평가부만 "Ruler가 POST해 준 알림을 받아 상태 머신에 넣는" 구현으로 바뀐다.

### A.5 권장 설계 개요 (B안)

#### A.5.1 구성

```
┌──────────────┐   정책 CRUD    ┌──────────────────┐
│  프론트 알람  │ ─────────────▶│ AlarmPolicyService │──▶ alarm_policies / _targets / _recipients
└──────────────┘               └──────────────────┘
                                          │ 활성 정책
                               ┌──────────▼──────────┐   PromQL 즉시 쿼리
                               │ AlarmEvaluator(60s)  │ ─────────────▶ Thanos Query
                               │  @Scheduled+ShedLock │ ◀─────────────  벡터(자원별 값)
                               └──────────┬──────────┘
                                          │ 상태 전이(normal→pending→firing→resolved)
                               ┌──────────▼──────────┐
                               │ alarm_states / alarm_history │
                               └──────────┬──────────┘
                                          │ firing 진입 시 전송 작업 생성
                               ┌──────────▼──────────┐   ┌────────────┐  ┌────────────┐
                               │ AlarmNotifier        │──▶│ EmailSender │  │ SmsSender  │
                               │ (수신자 전개·템플릿) │   └────────────┘  └────────────┘
                               └──────────┬──────────┘
                                          ▼
                             alarm_deliveries / alarm_delivery_recipients
```

#### A.5.2 상태 머신 (정책 × 자원 단위)

| 현재 | 조건 | 다음 | 부수 효과 |
|---|---|---|---|
| NORMAL | 임계 충족 | PENDING (durationSeconds > 0) 또는 FIRING (즉시) | FIRING이면 이력 생성 + 전송 |
| PENDING | 임계 충족 지속 ≥ duration | FIRING | 이력 생성 + 전송 |
| PENDING | 임계 미충족 | NORMAL | 없음 |
| FIRING | 임계 미충족 | RESOLVED → NORMAL | 이력 `resolvedAt` 기록 (해소 알림은 옵션) |
| FIRING | 임계 충족 | FIRING | 재알림 없음(중복 억제). 재알림 간격은 정책 옵션으로 확장 가능 |

- 자원 식별은 자원 탐색기와 동일: 물리 호스트 `instance`, Tumblebug VM `tb_ns/tb_infra/tb_node`.
- 관측값·기준 문자열(`CPU Used > 80%`)은 발생 시점에 이력 행에 **스냅샷**으로 저장한다(정책이 나중에 바뀌어도 이력은 불변).

#### A.5.3 테이블 (신규)

| 테이블 | 주요 컬럼 |
|---|---|
| `alarm_policies` | id, name, type(METRIC), role_name, area_id, area_kind, resource_type, target_scope, metric_type, metric, operator, threshold, level, duration_seconds, channels, description, enabled, created_by, created_at, updated_at |
| `alarm_policy_targets` | policy_id, resource_id(assets.id 또는 TB:{ns}/{infra}/{node}) |
| `alarm_policy_recipients` | policy_id, target_type(INDIVIDUAL/ORGANIZATION), target_id |
| `alarm_states` | policy_id, resource_id, state, since, last_value, last_evaluated_at |
| `alarm_history` (재정의, **구현 완료**) | id, source, policy_id, policy_name, level, resource_type, resource_id, resource_name, role_name, area_id, area_kind, metric, criterion, observed_value, unit, occurred_at, resolved_at, status, acknowledged_at, acknowledged_by, ack_content, fingerprint, inhibited, labels_json, delivery_count |
| `alarm_deliveries` | id, history_id, target_type, target_id, target_name, channel, subject, body, created_at |
| `alarm_delivery_recipients` | delivery_id, user_id, name, address, status(SUCCESS/SENDING/FAILED), sent_at, fail_reason |

기존 `alarm_rules`·`AlarmController(@Deprecated)`는 정책 원장으로 대체 후 제거한다.

#### A.5.4 전송

- 발송은 평가 트랜잭션과 분리(`@TransactionalEventListener(AFTER_COMMIT)` 또는 별도 큐 테이블 폴링)해 SMTP 지연이 평가 주기를 막지 않게 한다.
- 수신자 전개: 개인 → 그대로, 조직 → 발송 시점에 구성원 조회. 수신자별 행을 SENDING으로 먼저 만들고 결과로 갱신하면 프론트의 "전송중" 상태가 자연스럽게 나온다.
- 발송기는 `NotificationSender` 인터페이스(Email 구현: Spring Mail, SMS 구현: 게이트웨이 확정 후). 실패 시 제한 재시도(예: 3회, 지수 백오프) 후 FAILED + 사유 저장.
- 메시지 템플릿은 정책 레벨·메트릭·자원명·관측값·시각을 치환한 결과를 `alarm_deliveries.body`에 저장한다.

#### A.5.5 기존 자산 재사용

- PromQL 표준식: `HostDetailMetricsQueryService`, `HostCategoryMetricsQueryService`의 CPU/Memory/File System 식 → 메트릭 카탈로그(`GET /policies/metric-catalog`)와 평가 쿼리에 공용.
- 자원 스코프: `ResourceScopeService`, `TumblebugPanelSupport` → 정책 대상 후보 목록, `targetScope=ALL` 전개, 역할 필터.
- 미리보기 시계열: 자원 탐색기 `metrics/trend`와 동일 조회기.

### A.7 참고: A안·C안을 택할 때 필요한 추가 작업

나중에 C안으로 전환할 때를 위해 기록해 둔다.

- `thanos-rule` 컨테이너 추가(`--query`로 Thanos Query 지정, `--alertmanagers.url`로 백엔드 지정, 규칙 파일 볼륨).
- 백엔드: 정책 → rule 그룹 YAML 생성기, 파일 기록 후 `POST /-/reload`, 실패 시 롤백.
- 백엔드: `POST /api/v2/alerts`(Alertmanager API v2 호환) 수신 엔드포인트 — Ruler가 firing/resolved 알림을 주기적으로 재전송하므로 멱등 처리 필요.
- rule 라벨에 `policy_id`, `resource_id`, `level`을 실어 백엔드가 원장과 조인.
- A안(Alertmanager까지)은 여기에 `alertmanager` 컨테이너, 라우트·수신기 YAML 생성, Webhook 수신기가 더 붙는다. 위 3.1의 제약으로 권장하지 않는다.

### B.3 Alertmanager를 여전히 도입하지 않는 이유 (재확인)

Confluence C1·C3는 표준 스택을 조사한 권고이고, 화면 요구와 맞춰 보면 Alertmanager가 담당하는 "라우팅·발송" 부분은 우리가 직접 해야 한다.

- 프론트가 요구하는 **수신자 개인별 전송 결과·실패 사유·전송 일시, 조직 단위 성공/전송중/실패 카운트, 발송 본문 저장, 확인 내용·확인자**는 Alertmanager에 없다. Webhook으로 받아 백엔드가 발송해야 하므로 Alertmanager는 그룹핑·억제만 남는다.
- 정책·조직 수신자가 바뀔 때마다 alertmanager.yml 재생성·리로드가 필요해 사용자 관리와 결합된다.
- 대신 C1·C3가 말하는 가치(억제·데드맨·사이트 생존성·webhook 수신)는 **백엔드 평가기에 기능으로 넣고**, 표준 스택과는 **Alertmanager API v2 호환 수신 엔드포인트**로 만난다. 세부1·3·KETI가 자기 Alertmanager에서 우리 엔드포인트로 알림을 보내면 그대로 원장에 들어온다. 이렇게 하면 "우리는 커스텀 컨트롤러(C3), 남들은 Alertmanager"라는 구도가 성립한다.

```
                        ▼                           ▼
              [전송 계층]                    [이벤트 발행]
               Email / SMS / WEBHOOK          ApplicationEvent → 스케줄러(온도 2단계 조치),
               alarm_deliveries(+recipients)  포털 로그(ALARM), GET /events, 구독자 webhook
```

#### B.4.2 알람 원천(source) 4종

| source | 만들어지는 곳 | 정책 필요 | 비고 |
|---|---|---|---|
| `POLICY` | 사용자 정책 평가기 | 있음 | 이전 설계 그대로(메트릭 묶음 평가, 정책×자원 상태 머신) |
| `SYSTEM` | 내장 규칙 평가기 | 없음(코드 내장, 임계값만 설정) | 에이전트 다운·사이트 생존성·데드맨·연동 장애 |
| `EXTERNAL` | Alertmanager v2 호환 수신 | 없음(라벨 매핑 규칙만) | 세부1·3·KETI. `fingerprint`로 멱등, `endsAt`로 해소 |
| `EVENT` | Redfish EventService 등 장치 이벤트 | 없음 | 후속. 하드웨어 임계 이벤트(온도·팬·전원) |

#### B.4.3 내장 시스템 규칙 (Confluence 반영)

| 규칙 | 조건 | 레벨 | 대상 | 근거 |
|---|---|---|---|---|
| 에이전트 다운 | `up == 0` 5분 지속 | WARNING | monitoring_target 단위 | C4 #52 |
| 사이트 생존성 | MDC의 마지막 remote_write 수신이 N분 초과(`time() - max(timestamp(up{mdc_id=…}))`) | CRITICAL | MDC | C1 |
| 데드맨 | 평가기가 매 주기 `aims_alarm_evaluator_heartbeat`를 갱신하지 않으면(외부 Watchdog 또는 자체 스레드) | CRITICAL | 포털 | C1 |
| 연동 장애 | Tumblebug 429/5xx 연속, Thanos degraded, Loki `/ready` 실패 | WARNING | 포털 | 자원 탐색기 기존 판정 재사용 |
| GPU 스로틀 | `DCGM_FI_DEV_CLOCK_THROTTLE_REASONS` 열 비트 지속 | WARNING | GPU | C3 §4.1 |

임계값·지속시간은 `application.yml`(`aims.alarm.system-rules.*`)로 두고 화면에는 정책 목록에 "시스템" 구분으로 읽기 전용 노출한다.

#### B.4.4 억제(inhibition)

- 사이트 생존성(MDC) 알람이 FIRING이면 그 MDC 하위 노드·VM·GPU의 POLICY/SYSTEM 알람은 **발생은 기록하되 전송하지 않는다**(`inhibited = true`). 사이트 복구 시 여전히 참인 알람만 그때 전송한다.
- 에이전트 다운 알람이 FIRING이면 같은 자원의 메트릭 정책 알람은 억제한다(데이터 부재로 인한 오탐 방지).
- 억제 관계는 코드 내장 2단(MDC → 자원, 에이전트 → 자원)으로 시작하고, 사용자 정의 억제는 두지 않는다.

#### B.4.5 전송 채널과 대외 구독

- 채널 enum에 `WEBHOOK` 추가: `AlarmChannel = EMAIL | SMS | WEBHOOK`.
- 구독 원장 `alarm_subscriptions`(id, name, url, secret, filter(level·source·mdcId), enabled, created_by). 세부3가 `POST /api/v1/monitoring/alarms/subscriptions`로 등록하고, 발생·해소 시 Alertmanager webhook 페이로드 형식(`alerts[]`, `status`, `labels`, `annotations`)으로 전송한다 — 수신 측이 표준 도구를 그대로 쓸 수 있다.
- `GET /api/v1/monitoring/events?from&to&level&source&mdcId` — C5의 `GET /events`. 초안의 `EventController` 경로를 그대로 쓰고(C.2), `events` 원장에서 발생·해소 이벤트를 시간순으로 내준다(세부3용 읽기 전용). 새 경로 `/alarms/events`는 만들지 않는다.

#### B.4.6 알람 → 조치 훅

- 알람 처리기가 FIRING/RESOLVED 전이 시 `AlarmStateChangedEvent`(policyId, source, level, resourceId, mdcId, metric, value)를 발행한다.
- 스케줄러는 이를 구독해 C3 2단계(허용 온도 초과 → 신규 배치 차단·워크로드 이전 제안)를 구현한다. 조치 로직과 안전장치(자동/승인)는 스케줄러 설계에서 정한다. 알람 모듈은 이벤트 발행까지만 책임진다.
- 포털 로그 `ALARM` 타입 기록도 같은 이벤트를 구독해 남긴다(docs/08 §3.2).

#### B.4.9 범위 밖으로 명시할 것

- 사이트 로컬 알림(C2): 중앙 포털 범위 밖. 세부1 사이트 구축 시 로컬 Prometheus+Alertmanager를 두고, 그 Alertmanager가 우리 `POST /api/v2/alerts`로도 보내면 중앙 이력에 합류한다.
- SLO 번레이트(C1): 1차 제외.
- 자동 조치 실행(C3 2·3단계): 스케줄러 영역. 알람은 이벤트 발행까지.

### B.5 성능 관점 (이전 분석 유지)

정책 평가는 메트릭 단위 묶음(주기당 쿼리 수 = 메트릭 종류 수)으로 정책 수와 무관하게 유지한다. 내장 규칙은 메트릭 4~5개가 추가될 뿐이다. 외부 수신은 push라 평가 부하가 없고, fingerprint 인덱스로 멱등 처리한다. 억제 판정은 메모리 상태(MDC·에이전트 FIRING 집합) 조회라 비용이 없다.

## C부. 기존 초안(feat/event-alarm) 계승 규칙

`feat/event-alarm` 브랜치(develop 에 이미 병합)에 있는 초안 — `AlarmRule`·`AlarmHistory`·`Event` 엔티티, `AlarmController`(`/alarms/rules`, `/alarms/history`), `EventController`(`/events`), `AlarmEvaluationService`(1분 주기, PromQL 4종) — 는 방향이 이 설계와 같다. 백엔드가 주기적으로 Thanos 를 평가하고, 라벨로 자원을 식별하고, 이력과 이벤트를 원장에 남긴다. 아래는 그 초안을 B부 설계로 넓힐 때 무엇을 잇고 무엇을 바꾸는지다.

### C.1 잇는 것

| 초안 | 계승 방식 |
|---|---|
| `AlarmEvaluationService` `@Scheduled(60s)` 백엔드 평가 | 그대로 평가기의 골격. 규칙 순회를 (메트릭, 주기) 묶음 평가로 바꾸고 상태 머신·억제를 얹는다(A.5.2, B.4.4) |
| `avg by(instance, mdc_id)` 라벨 조인 | 평가 결과 벡터를 `instance`(물리 호스트)·`tb_ns/tb_infra/tb_node`(Tumblebug VM) 라벨로 자원에 대응시키고, `mdc_id` 라벨로 배포영역(MDC)을 채운다. 자원 탐색기의 `MetricSelector`·`monitoring_target.asset_id` 매핑을 재사용 |
| `AlarmHistory.status` OPEN → ACKNOWLEDGED → RESOLVED | 이력 행의 상태 어휘로 유지. 평가기 내부 상태(NORMAL/PENDING/FIRING)는 `alarm_states` 에만 두고 이력에는 노출하지 않는다. 확인(ack)은 ACKNOWLEDGED + `acknowledged_at/by/content` |
| `Event` 원장 + `GET /api/v1/monitoring/events` | **대외 이벤트 발행 원장**으로 역할을 정한다. 알람 발생·해소, 내장 시스템 규칙(사이트 생존성·에이전트 다운), 외부 수신 알람이 한 줄씩 들어가고, 세부3 `GET /events`(C5)와 WEBHOOK 구독 발송이 여기서 읽는다. 컬럼에 `source`(POLICY/SYSTEM/EXTERNAL/EVENT), `alarm_history_id`, `resource_id`, `labels_json` 을 더한다 |
| 알람 발생 시 `Event` 동시 적재 | 유지. 단 같은 트랜잭션이 아니라 `AlarmStateChangedEvent`(B.4.6) 구독으로 적재해 평가 트랜잭션과 분리한다 |
| 연산자 `gt/gte/lt/lte/eq` | `AlarmConditionOperator` enum(GT/GTE/LT/LTE/EQ)으로 대문자화. 프론트 한글(초과/이상/미만/이하)은 프론트가 코드로 변환 |

### C.2 바꾸는 것

| 초안 | 바꾸는 이유 | 대체 |
|---|---|---|
| `alarm_rules`(name, metricName, condition, threshold, severity, notifyChannel) | 역할·배포영역·자원 유형·대상 범위·수신자·채널 다중·지속시간을 담을 수 없다 | `alarm_policies` + `alarm_policy_targets` + `alarm_policy_recipients`(A.5.3). 기존 `alarm_rules` 행은 수동 이관(운영 데이터가 있으면) 후 테이블 삭제 |
| `METRIC_PROMQL` 4종 하드코딩(`cpu_usage`, `mem_usage`, `disk_usage`, `gpu_temperature`) | 프론트 카탈로그(CPU Used(%), Memory Used/Available, FS Used, Inode, …)와 어휘가 다르고 확장 불가 | **구현됨(2026-09-08)** — `AlarmMetric` enum 이 카탈로그(`GET /alarms/policies/metric-catalog?resourceType=`)와 PromQL 템플릿(`promql(groupBy, matchers, window)`)을 한 곳에 정의. 코드값 8종: `CPU_USED_PERCENT`, `MEMORY_USED_PERCENT`, `MEMORY_AVAILABLE_GB`, `FS_USED_PERCENT`, `INODE_USED_PERCENT`, `GPU_UTIL`, `GPU_MEMORY_USED_PERCENT`, `GPU_TEMP`. 유형 라벨(CPU/Memory/File System/GPU)은 프론트 옵션 값과 동일. 자원 유형별 적용: node 전체, vm은 GPU 제외(할당 원장 전), gpu는 GPU만. 초안 이름 4종은 `AlarmMetric.resolve()` 별칭. 평가기(`AlarmEvaluationService`)도 같은 날 교체 — 활성 규칙을 메트릭별로 묶어 메트릭당 쿼리 1회(`promql("instance, mdc_id, tb_ns, tb_infra, tb_node", null, "5m")`), `tb_*` 라벨이 있으면 VM·Namespace 영역, 없으면 호스트·MDC 영역으로 기록, criterion 은 `AlarmMetric.criterion()` |
| 조건 참이면 매 주기 새 이력 생성(중복 억제 없음) | 1분마다 행이 무한 생성 | 정책×자원 상태 머신 — FIRING 진입 시 1건, RESOLVED 전이 시 갱신(A.5.2) |
| 단일 시점 비교 | 지속시간(for) 미지원 | `duration_seconds` + PENDING 상태 |
| `severity`·`condition`·`notifyChannel` 문자열 컬럼 | 대소문자·오타 취약 | `AlarmLevel`(INFO/WARNING/CRITICAL), `AlarmConditionOperator`, `AlarmChannel`(EMAIL/SMS/WEBHOOK) enum |
| `AlarmController` `/alarms/rules`, `/alarms/history`(엔티티 직노출, 페이징 없음) | 명세서 §18 구 계약. 프론트는 미사용(fixture) | `AlarmPolicyController`·`AlarmHistoryController`(develop 에 인터페이스 존재)로 대체 후 삭제. 명세서 §18 은 갱신 |
| `AlarmHistory(rule_id FK, mdc_id, instance, metric_value, severity)` | 자원 유형·이름, 정책 스냅샷(criterion), 역할, 확인 정보, source 가 없다 | `alarm_history` 재정의(A.5.3 + B.4.7). `rule_id` FK 대신 `policy_id` + 정책명·기준 문자열 스냅샷 |
| 예외를 `log.debug` 로 삼킴 | 평가 장애가 보이지 않는다 | Thanos 조회 실패는 포털 로그 SYSTEM 으로 상태 변화 시 기록, 평가기 데드맨 규칙(B.4.3) |

### C.3 이관 순서

1. 새 원장(`alarm_policies`·`alarm_deliveries`·`alarm_subscriptions`·`events` 확장) 생성, `alarm_history` 는 같은 이름으로 재정의(DROP 후 재생성 — 초안 행은 폐기).
2. 기존 `alarm_rules` 행이 있으면 정책으로 이관(메트릭 별칭 매핑, 수신자는 비움). 평가기는 재정의된 `alarm_history` 에 기록한다(완료).
3. 새 `AlarmEvaluationService` 로 교체, 구 스케줄러 제거.
4. 프론트가 새 API 로 전환된 뒤 `AlarmController`(`/rules`)·`alarm_rules` 삭제. `/history`·`/history/{id}/status` 는 `/histories` 로 대체되어 이미 제거했다.
