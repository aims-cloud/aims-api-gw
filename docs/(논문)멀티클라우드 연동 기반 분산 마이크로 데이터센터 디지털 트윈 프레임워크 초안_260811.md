## 초록 (Abstract)

엣지 컴퓨팅의 확산에 따라 지리적으로 분산된 마이크로 데이터센터(Micro Data Center, MDC)의 수가 증가하고 있으나, 다수의 이기종 인프라를 통합적으로 관리하는 것은 여전히 어려운 과제이다. 기존의 데이터센터 관리 솔루션은 대규모 단일 데이터센터를 대상으로 설계되어, 분산 MDC 환경의 실시간 모니터링, 퍼블릭 클라우드 연동, 자원 최적화 요구를 충족하지 못한다. 본 논문에서는 디지털 트윈 개념을 적용하여 분산된 다수 MDC와 퍼블릭 클라우드를 통합 관리하는 5계층 아키텍처 기반의 플랫폼 'AIMS Cloud'를 제안한다. 물리 계층의 서버, GPU, 네트워크, 스토리지 자원을 Prometheus 에코시스템 기반으로 실시간 수집하고, VictoriaMetrics 시계열 데이터베이스에 저장하여 디지털 트윈 계층을 구성한다. 퍼블릭 클라우드 연동은 오픈소스 멀티클라우드 프레임워크인 Cloud-Barista를 활용하여 AWS, GCP, Azure 등 12개 CSP에 대한 통합 API를 제공한다. 프로토타입 구현 결과, MDC 자원 상태의 실시간 동기화 지연이 15초 이내이며, 시간별 자동 집계를 통한 미터링·빌링 데이터 생성이 가능함을 확인하였다. 본 연구의 기여는 (1) 분산 MDC를 위한 5계층 디지털 트윈 아키텍처 제안, (2) 오픈소스 기반 멀티클라우드 통합 연동 구현, (3) 시계열 DB 기반 실시간 메트릭 수집·집계·분석 파이프라인 구현이다.

**키워드:** 디지털 트윈, 마이크로 데이터센터, 자원 관리, 멀티클라우드, 시계열 데이터베이스, Cloud-Barista, Prometheus

## 1. 서론

### 1.1 연구 배경

5G/6G 통신 환경의 확산, IoT 디바이스의 폭발적 증가, 그리고 저지연 서비스에 대한 수요 증가로 인해 엣지 컴퓨팅(Edge Computing)이 주목받고 있다[1]. 이에 따라 사용자와 가까운 위치에 소규모 컴퓨팅 자원을 배치하는 마이크로 데이터센터(Micro Data Center, MDC)의 구축이 활발히 이루어지고 있다. MDC는 기존 대형 데이터센터와 달리 수 대에서 수십 대 규모의 서버로 구성되며, 대학, 연구소, 공공기관 등에 분산 배치된다[2].

그러나 지리적으로 분산된 다수의 MDC를 운영하는 과정에서 다음과 같은 문제가 발생한다. 첫째, 각 MDC가 독립적으로 관리되어 전체 인프라에 대한 통합적인 가시성이 부족하다. 둘째, MDC의 자원이 부족할 때 퍼블릭 클라우드로 워크로드를 확장(Cloud Bursting)해야 하나, 이기종 클라우드 간 통합 관리 체계가 미비하다. 셋째, CPU, 메모리, GPU, 전력, 온도 등 다양한 자원의 실시간 모니터링과 이를 기반으로 한 과금·최적화가 체계적으로 이루어지지 않는다.

### 1.2 문제 정의

기존 데이터센터 인프라 관리(DCIM) 솔루션은 대규모 단일 데이터센터를 대상으로 설계되어 있어, 분산 MDC 환경에 직접 적용하기 어렵다. 구체적으로 다음과 같은 한계가 있다.

- **분산 환경 미고려:** 기존 DCIM은 단일 사이트를 전제로 하며, 다수 MDC의 자원을 통합 조회·비교·제어하는 기능이 부족하다.
- **멀티클라우드 연동 부재:** 온프레미스 MDC와 퍼블릭 클라우드(AWS, GCP, Azure 등)를 하나의 인터페이스로 관리하는 기능이 없다.
- **실시간 디지털 트윈 부재:** 물리 인프라의 가상 복제본을 통한 실시간 상태 동기화, 이상 탐지, 용량 예측 등의 고도화된 분석이 어렵다.

### 1.3 연구 목적 및 기여

본 논문에서는 디지털 트윈(Digital Twin) 개념을 분산 MDC 환경에 적용하여 다수의 MDC와 퍼블릭 클라우드를 통합 관리하는 플랫폼 'AIMS Cloud'를 설계하고 구현한다. 본 연구의 주요 기여는 다음과 같다.

1. **분산 MDC를 위한 5계층 디지털 트윈 아키텍처 제안:** 물리 계층, 수집/연동 계층, 디지털 트윈 계층, 서비스 계층, 분석/예측 계층으로 구성된 체계적인 아키텍처를 정의한다.
2. **오픈소스 기반 멀티클라우드 통합 연동:** Cloud-Barista 프레임워크를 활용하여 12개 CSP에 대한 통합 VM, 네트워크, 스토리지 관리 API를 구현한다.
3. **시계열 DB 기반 메트릭 수집·집계·분석 파이프라인:** Prometheus와 VictoriaMetrics를 활용한 실시간 수집, 자동 시간별 집계, SQL 기반 비즈니스 분석 체계를 구현한다.

### 1.4 논문 구성

본 논문의 구성은 다음과 같다. 2장에서는 디지털 트윈, 데이터센터 관리, 멀티클라우드 관련 연구를 분석한다. 3장에서는 제안하는 5계층 디지털 트윈 아키텍처와 핵심 설계를 기술한다. 4장에서는 프로토타입 구현 내용을 설명한다. 5장에서는 실험 환경과 성능 평가 결과를 제시한다. 6장에서는 결론과 향후 연구 방향을 논의한다.

## 2. 관련 연구

### 2.1 디지털 트윈 기술

디지털 트윈은 물리적 시스템의 가상 복제본으로, 센서 데이터를 기반으로 물리 시스템과 실시간으로 동기화되며, 모니터링, 시뮬레이션, 예측, 최적화에 활용된다[3]. ISO 23247은 제조 환경에서의 디지털 트윈 프레임워크를 정의하며, 물리 엔티티, 데이터 수집, 디지털 트윈 코어, 사용자 도메인의 4계층 구조를 제시한다[4].

최근 디지털 트윈의 적용 범위가 제조업에서 스마트시티, 헬스케어, 에너지, 데이터센터 등으로 확장되고 있다. 특히 엣지 컴퓨팅 환경에서의 디지털 트윈은 자원 제약 환경에서의 실시간 데이터 처리와 고가용성 확보에 초점을 맞추고 있다[5].

### 2.2 데이터센터 디지털 트윈

데이터센터 디지털 트윈에 관한 연구는 주로 대형 데이터센터의 냉각 최적화와 에너지 효율 개선에 집중되어 있다. Athavale(2024)은 IEEE Computer에서 데이터센터 디지털 트윈의 시각화 및 모델링 기법을 개관하였다[6]. 삼성SDS(2023)는 CFD(Computational Fluid Dynamics) 기반 열 시뮬레이션을 통해 데이터센터 냉각 효율을 개선하는 디지털 트윈 사례를 제시하였다[7]. Lyu et al.(2026)은 디지털 트윈 기반 냉각 시스템 최적화를 제안하였다[8].

그러나 이들 연구는 대규모 단일 데이터센터를 대상으로 하며, 지리적으로 분산된 소규모 MDC의 통합 관리는 다루지 않는다. 또한 퍼블릭 클라우드와의 하이브리드 연동도 고려하지 않는다.

국내에서는 이갑래와 김영식(2022)이 마이크로 데이터센터의 환경 모니터링 시스템을 개발하여 IoT 센서 기반 데이터 수집을 구현하였으나[9], 디지털 트윈 개념의 적용이나 멀티클라우드 연동은 포함하지 않았다.

### 2.3 멀티클라우드 관리 플랫폼

멀티클라우드 관리의 핵심 과제는 CSP별로 상이한 API, 자원 모델, 인증 체계를 통합하는 것이다. Cloud-Barista[10]는 ETRI가 주관하는 오픈소스 멀티클라우드 프레임워크로, CB-Spider(통합 드라이버)와 CB-Tumblebug(인프라 오케스트레이션)을 핵심 컴포넌트로 제공한다. CB-Spider는 AWS, GCP, Azure, NCP, NHN Cloud 등 12개 CSP에 대해 VPC, VM, 디스크, NLB 등의 통합 REST API를 제공하며, CB-Tumblebug은 네임스페이스 기반으로 멀티클라우드 인프라를 생성·관리·제어하는 오케스트레이션 기능을 제공한다.

기존 연구에서 Cloud-Barista를 활용한 인프라 관리 사례는 있으나, 디지털 트윈 개념과 결합하여 분산 MDC의 온프레미스 자원까지 통합 관리하는 연구는 찾아보기 어렵다.

### 2.4 시계열 데이터 기반 인프라 모니터링

인프라 모니터링에 널리 사용되는 Prometheus[11]는 Pull 기반 메트릭 수집 모델을 채택하며, node_exporter, dcgm_exporter, ipmi_exporter 등 다양한 Exporter를 통해 서버, GPU, 물리 장비의 메트릭을 수집한다. VictoriaMetrics[12]는 Prometheus와 호환되는 장기 저장소로, 뛰어난 압축률과 단일 바이너리 운영의 단순성이 특징이다.

## 3. 시스템 설계

### 3.1 5계층 디지털 트윈 아키텍처

본 논문에서는 분산 MDC 환경에 적합한 5계층 디지털 트윈 아키텍처를 제안한다. Fig. 1은 전체 아키텍처를 나타낸다.

**Fig. 1. 5계층 디지털 트윈 아키텍처**

```
┌───────────────────────────────────────────────────────────┐
│ ⑤ 분석/예측 계층 (Analytics & Prediction Layer)            │
│   자원 최적화 진단 | 비용 분석 | 용량 예측 | 버스팅 판단      │
├───────────────────────────────────────────────────────────┤
│ ④ 서비스 계층 (Service Layer)                              │
│   REST API | 인증/인가 | 미터링 | 빌링 | 대시보드            │
├───────────────────────────────────────────────────────────┤
│ ③ 디지털 트윈 계층 (Digital Twin Layer)                     │
│   시계열 메트릭 저장소 (VictoriaMetrics)                     │
│   자산 모델 DB (PostgreSQL)                                │
│   토폴로지 모델 | 랙실장도 모델 | 자원 상태 모델              │
├───────────────────────────────────────────────────────────┤
│ ② 수집/연동 계층 (Collection & Integration Layer)           │
│   Prometheus + Exporter (MDC 온프레미스)                    │
│   Cloud-Barista CB-Spider/CB-Tumblebug (퍼블릭 클라우드)    │
├───────────────────────────────────────────────────────────┤
│ ① 물리 계층 (Physical Layer)                               │
│   MDC-A (서울)    MDC-B (대전)    MDC-C (부산)              │
│   서버·GPU·SAN    서버·GPU·SAN    서버·GPU·SAN              │
│                                                           │
│   AWS            GCP            Azure          NCP        │
└───────────────────────────────────────────────────────────┘
```

각 계층의 역할은 다음과 같다.

**① 물리 계층 (Physical Layer):** 지리적으로 분산된 다수의 MDC와 퍼블릭 클라우드 인프라로 구성된다. 각 MDC는 물리 서버, GPU/NPU, 스토리지, 네트워크 장비(SAN 스위치 등)를 포함한다.

**② 수집/연동 계층 (Collection & Integration Layer):** 물리 계층의 데이터를 수집하여 상위 계층에 전달하는 역할을 한다. MDC 온프레미스 자원은 Prometheus 에코시스템의 Exporter를 통해 Pull 방식으로 수집하며, 퍼블릭 클라우드 자원은 Cloud-Barista의 CB-Spider를 통해 REST API로 조회한다.

**③ 디지털 트윈 계층 (Digital Twin Layer):** 물리 인프라의 가상 복제본을 구성·유지하는 핵심 계층이다. VictoriaMetrics에 시계열 메트릭을 저장하고, PostgreSQL에 자산 모델(서버, 네트워크, 랙 정보)을 관리한다. 이 계층이 물리 계층과 15초 주기로 동기화됨으로써 디지털 트윈의 실시간성을 보장한다.

**④ 서비스 계층 (Service Layer):** REST API를 통해 사용자(포탈 Frontend)에게 기능을 제공한다. 인증/인가, VM 라이프사이클 관리, 미터링 집계, 빌링, 대시보드 등의 비즈니스 로직을 담당한다.

**⑤ 분석/예측 계층 (Analytics & Prediction Layer):** 디지털 트윈 계층에 축적된 시계열 데이터를 분석하여 자원 최적화 진단, 비용 절감 권고, 용량 예측, 퍼블릭 클라우드 버스팅 판단 등의 고도화된 기능을 제공한다.

### 3.2 물리-디지털 트윈 매핑 모델

디지털 트윈의 핵심은 물리 엔티티와 가상 표현 간의 일대일 매핑이다. Table 2는 MDC 물리 엔티티와 디지털 트윈 표현의 매핑을 정의한다.

**Table 2. 물리-디지털 트윈 매핑**

| 물리 엔티티 | 디지털 트윈 표현 | 수집 방법 | 수집 주기 |
|------------|----------------|----------|----------|
| 컴퓨팅 노드 (CPU/MEM) | 자원 상태 모델 (사용률 시계열) | node_exporter | 15초 |
| GPU/NPU | GPU 상태 모델 (사용률, 온도, 전력) | dcgm_exporter | 15초 |
| 물리 서버 BMC | 물리 서버 모델 (전력, 온도, 팬) | ipmi_exporter | 60초 |
| SAN 스위치 | SFP 포트 모델 (광출력, 에러율) | snmp_exporter | 60초 |
| 네트워크 토폴로지 | 연결 그래프 모델 | SNMP + 설정 DB | 300초 |
| 랙 장비 배치 | 랙실장도 모델 | 자산관리 DB | 수동/변경 시 |
| 퍼블릭 클라우드 VM | VM 상태 모델 | CB-Spider API | 60초 |

### 3.3 데이터 수집 아키텍처

Fig. 2는 MDC 자원 데이터의 수집 및 저장 흐름을 나타낸다.

**Fig. 2. 데이터 수집 아키텍처**

```
[MDC 각 노드]                  [수집 서버]               [AIMS 서버]

node_exporter (:9100)
dcgm_exporter (:9400)  ──Pull──▶ Prometheus ──remote_write──▶ VictoriaMetrics
ipmi_exporter (:9290)              (:9090)                    (:8428)
snmp_exporter (:9116)                                            │
                                                        PromQL 쿼리 (실시간)
                                                                 │
                                                          AIMS Backend
                                                          │           │
                                                  매시간 집계     REST API
                                                          │           │
                                                     PostgreSQL    Frontend
                                                  (metering_hourly)
```

Prometheus의 Pull 기반 수집 모델을 채택한 근거는 다음과 같다. (1) 서비스 디스커버리를 통한 동적 대상 관리가 가능하다. (2) 네트워크 방화벽 환경에서 수집 서버에서 대상으로 접근하는 방향이 보안적으로 유리하다. (3) Exporter 에코시스템이 풍부하여 node, GPU, IPMI, SNMP 등 다양한 데이터 소스를 일관되게 수집할 수 있다.

시계열 저장소로 VictoriaMetrics를 선정한 근거는 Table 3과 같다.

**Table 3. 시계열 DB 비교**

| 항목 | VictoriaMetrics | InfluxDB | TimescaleDB |
|------|:-:|:-:|:-:|
| Prometheus 호환 | 네이티브 | 어댑터 필요 | 어댑터 필요 |

### 3.4 멀티클라우드 연동 설계

**Fig. 3. 멀티클라우드 연동 구조**

```
AIMS Backend
    │
    ├──REST──▶ CB-Spider (통합 드라이버, :1024)
    │              │
    │              ├──▶ AWS API
    │              ├──▶ GCP API
    │              ├──▶ Azure API
    │              └──▶ NCP, NHN, KT, ... API
    │
    └──REST──▶ CB-Tumblebug (오케스트레이션, :1323)
                   │
                   └──▶ CB-Spider (내부 호출)
```

AIMS Backend는 CB-Spider/CB-Tumblebug의 REST API를 호출하여 CSP 자원을 관리한다. 이를 통해 AIMS 자체적으로 각 CSP의 API를 직접 연동할 필요가 없으며, Cloud-Barista가 지원하는 CSP가 추가될 때 AIMS의 코드 변경 없이 자동으로 확장된다.

### 3.5 미터링 및 빌링 설계

디지털 트윈 계층에 축적된 시계열 데이터를 기반으로 미터링(자원 사용량 계량)과 빌링(과금)을 수행한다. Fig. 4는 미터링-빌링 데이터 흐름을 나타낸다.

**Fig. 4. 미터링-빌링 데이터 흐름**

```
VictoriaMetrics (실시간 메트릭)
       │
       │ 매시간 @Scheduled
       │ PromQL 범위 쿼리
       ▼
metering_hourly (PostgreSQL)
       │ avg_value, max_value, min_value, sample_count
       │
       │ SQL JOIN
       ▼
pricing_policy (가격 정책 테이블)
       │
       ▼
청구 금액 = Σ(사용량 × 단가)
```

시간별 집계 테이블(metering_hourly)은 MDC ID, 자원 ID, 메트릭명, 평균/최대/최소값을 저장하며, 가격 정책 테이블과 SQL JOIN을 통해 청구 금액을 산정한다.

SpiderClient와 TumblebugClient를 Spring의 RestClient로 구현하여 CB-Spider와 CB-Tumblebug의 REST API를 호출한다. Fig. 5는 VM 생성 시의 연동 흐름을 나타낸다.

```
         응답 반환
```

### 4.4 메트릭 수집 및 디지털 트윈 동기화 구현

**수집 에이전트 관리:** MonitoringTarget 엔티티를 통해 각 MDC의 수집 대상(exporter 엔드포인트)을 관리한다. ResourceCollectorService는 5분 주기로 Prometheus의 `up` 메트릭을 조회하여 에이전트의 생존 상태를 자동 갱신한다.

**실시간 조회:** MonitoringService는 VictoriaMetricsClient를 통해 PromQL 쿼리를 실행하고 결과를 DTO(RealtimeUsageResponse, GpuStatusResponse 등)로 변환하여 Frontend에 제공한다.

**시간별 집계:** MeteringAggregationService는 @Scheduled 어노테이션으로 매시간 정각에 실행되며, VictoriaMetrics에서 지난 1시간의 메트릭을 PromQL로 조회하여 평균/최대/최소값을 계산하고 PostgreSQL의 metering_hourly 테이블에 적재한다.

### 4.5 API 명세 자동 생성

springdoc-openapi를 활용하여 Swagger UI 기반의 API 명세를 자동 생성한다. 24개 컨트롤러에 @Tag 어노테이션을 적용하여 기능별로 분류하며, Frontend 개발자가 브라우저에서 API 목록, 파라미터, 응답 형식을 확인하고 직접 테스트할 수 있다.

## 6. 결론 및 향후 연구

### 6.1 결론

본 논문에서는 디지털 트윈 개념을 적용하여 분산된 다수의 마이크로 데이터센터와 퍼블릭 클라우드를 통합 관리하는 플랫폼 AIMS Cloud를 설계하고 구현하였다. 제안한 5계층 디지털 트윈 아키텍처는 물리 인프라의 실시간 상태를 가상 복제본으로 유지하며, Prometheus 에코시스템을 통한 15초 주기의 메트릭 수집, VictoriaMetrics를 통한 장기 저장, Cloud-Barista를 통한 12개 CSP 통합 연동을 구현하였다.

기존 연구가 대형 단일 데이터센터의 냉각 최적화에 집중한 것과 달리, 본 연구는 분산 소규모 MDC의 통합 관리, 온프레미스-퍼블릭 하이브리드 연동, 메트릭 기반 미터링·빌링까지 포괄하는 점에서 차별성을 갖는다. 또한 전체 시스템을 오픈소스 기반으로 구현하여 재현성과 확장성을 확보하였다.

### 6.2 한계점

본 연구의 한계점은 다음과 같다. 첫째, 실제 운영 중인 다수 MDC에서의 대규모 검증이 이루어지지 않았다. 둘째, 디지털 트윈의 시뮬레이션 기능(What-if 분석)이 아직 구현되지 않았다. 셋째, 머신러닝 기반의 자원 사용량 예측 모델이 포함되지 않았다.

### 6.3 향후 연구

향후 연구 방향은 다음과 같다.

1. **What-if 시뮬레이션:** 서버 추가/제거, 워크로드 이동 등의 변경 사항을 디지털 트윈 상에서 사전 시뮬레이션하는 기능을 개발한다.
2. **AI 기반 자원 예측:** 시계열 데이터에 LSTM 등의 딥러닝 모델을 적용하여 자원 사용량을 예측하고 자동 버스팅 판단 알고리즘을 개발한다.
3. **3D 시각화:** 랙실장도와 네트워크 토폴로지를 3D로 시각화하여 디지털 트윈의 직관성을 강화한다.
4. **Kubernetes 연동:** Cloud-Barista의 K8s 관리 API를 활용하여 멀티클라우드 컨테이너 오케스트레이션을 통합한다.
5. **대규모 실증:** 실제 운영 환경의 다수 MDC에서 장기간 운영하여 시스템의 안정성과 확장성을 검증한다.
