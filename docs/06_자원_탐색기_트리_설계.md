## 1. 개요

### 1.1 목적

자원 탐색기에서 역할별 물리 자원과 CB-Tumblebug가 관리하는 멀티클라우드 가상머신을 탐색하고, 각 자원에서 수집 가능한 모니터링 항목을 일관된 트리로 제공하기 위한 구조와 데이터 결합 기준을 정의한다.

### 1.2 적용 범위

- 물리 노드: MDC에 등록된 물리 호스트
- 가상자원: 물리 호스트에서 실행 중인 VM
- 가상머신: CB-Tumblebug에서 관리하는 OpenStack, AWS, Azure 및 GCP VM
- 모니터링: `node_exporter`, `dcgm_exporter`, `ipmi_exporter`, `snmp_exporter` 기반 지표
- Kubernetes 자원은 현재 범위에서 제외한다.

## 2. 확정 트리 구조

└─ 역할 (Role)

   │  └─ MDC
   │     └─ 물리 호스트
   │        ├─ 모니터링 항목 (수집 지원 여부에 따라 동적 구성)
   │        │  ├─ CPU
   │        │  ├─ Memory
   │        │  ├─ Disk
   │        │  │  ├─ Disk I/O
   │        │  │  └─ File System
   │        │  ├─ Network
   │        │  ├─ Process (집계)
   │        │  ├─ Service Status (systemd)
   │        │  ├─ Swap
   │        │  ├─ System
   │        │  ├─ GPU
   │        │  │  ├─ GPU 0
   │        │  │  └─ GPU 1
   │        │  └─ Hardware (IPMI / 지원되는 SNMP)
   │        │     ├─ Temperature
   │        │     ├─ Fan
   │        │     ├─ Power
   │        │     ├─ Voltage / Current
   │        │     ├─ Hardware Health
   │        │     └─ Hardware Events (요약)
   │        │
   │        └─ 가상자원
   │           ├─ 가상자원 (VM): web-01
   │           │  └─ 모니터링 항목 (수집 지원 여부에 따라 동적 구성)
   │           │     ├─ CPU

   │           │     ├─ Network
   │           │     ├─ Process (집계)
   │           │     ├─ Service Status (systemd)
   │           │     ├─ Swap

   │           │        ├─ GPU 0

                     ├─ Swap
                     ├─ System
                     └─ GPU
                        ├─ GPU 0

## 4. 자원 식별 및 연결 기준

### 4.1 물리 호스트와 가상자원 연결

물리 호스트 하위의 가상자원을 구성하려면 다음 관계가 명시적으로 확보되어야 한다.

```text
AIMS 물리 호스트 ID
↔ 1세부 가상화 플랫폼의 Host ID
↔ 1세부 가상자원 ID
```

물리 호스트는 AIMS 내부에서 `Asset.id`로 참조하고, 1세부 연동에서는 `Asset.source + Asset.externalId`를 동기화 키로 사용한다. 가상화 플랫폼이 제공하는 Host ID는 `Asset.externalId`와 연결한다. Host ID가 제공되지 않으면 hostname 또는 IP로 관계를 추정하지 않고, 해당 물리 호스트 아래에 가상자원을 표시하지 않는다.

### 4.2 Tumblebug VM 식별

Tumblebug의 ID는 관리 범위를 포함하여 사용한다.

```text
nsId + infraId + nodeId
```

Tumblebug Node의 내부 식별자와 CSP의 실제 가상머신을 구분할 수 있도록 `NodeInfo.cspResourceId`도 함께 저장한다. CSP 구분에는 `connectionName`과 `connectionConfig.providerName`을 사용한다.

트리 노드의 `resourceId` 형식은 다음과 같다. 1세부 가상자원의 `SEBU1:{externalId}`와 접두어로 자원 범위를 구분한다.

| 계층 | resourceId 형식 |
|------|-----------------|
| Namespace | `TB:{nsId}` |
| Infra | `TB:{nsId}/{infraId}` |
| NodeGroup | `TB:{nsId}/{infraId}/@{nodeGroupId}` |
| 미분류 | `TB:{nsId}/{infraId}/@unclassified` |
| Node(VM) | `TB:{nsId}/{infraId}/{nodeId}` |

Tumblebug `uid`(labelSelector 키)와 `cspResourceId`는 식별 키가 아니라 노드 속성으로 보관한다.

### 4.3 트리 노드 ID와 자원 ID

- `id`: 트리 내 위치를 나타내는 고유 ID
- `parentId`: 현재 트리 경로상의 부모 ID
- `resourceId`: 해당 자원 영역에서 실제 자원을 식별하는 안정적인 ID
- `type`: 트리 노드의 종류

물리 호스트 하위의 1세부 가상자원과 2세부 Tumblebug 가상머신은 서로 다른 자원 범위로 관리한다. 두 자원을 같은 VM으로 연결하거나 중복 제거하지 않는다.

## 5. 모니터링 항목 구성 규칙

### 5.1 기본 원칙

- 각 자원 아래의 모니터링 항목은 고정 목록을 무조건 생성하지 않고 수집 가능 여부에 따라 구성한다.
- exporter 등록 정보, 최근 수집 성공 여부 및 메트릭 카탈로그를 기준으로 지원 항목을 판단한다.
- 일시적인 수집 실패만으로 기존 메뉴를 제거하지 않는다. 지원 항목은 유지하고 상태를 `미수집` 또는 `UNKNOWN`으로 표시한다.
- 장치가 존재하지 않거나 exporter가 지원하지 않는 항목은 생성하지 않는다.

### 5.2 exporter별 항목

| Exporter | 트리 모니터링 항목 |
|----------|---------------------|
| `node_exporter` | CPU, Memory, Disk I/O, File System, Network, Process 집계, Service Status, Swap, System |
| `dcgm_exporter` | GPU 그룹 및 개별 GPU 장치 |
| `ipmi_exporter` | Temperature, Fan, Power, Voltage/Current, Hardware Health, Hardware Events 요약 |
| `snmp_exporter` | 설정된 MIB/OID에 따른 네트워크 및 하드웨어 지표 |

### 5.3 Disk 그룹

`Disk`는 화면용 그룹이며 하위 기능을 구분한다.

- `Disk I/O`: 블록 장치별 읽기·쓰기 처리량, IOPS 및 지연시간
- `File System`: 마운트별 전체·사용·가용 용량, 사용률 및 inode

### 5.4 Process와 Service Status

- `Process`: 프로세스·스레드 수 및 상태별 개수와 같은 집계 데이터
- `Service Status`: systemd unit의 Active, Inactive, Failed 상태

PID별 상세 프로세스 목록이나 명령행 정보는 기본 `node_exporter`만으로 제공된다고 가정하지 않는다.

### 5.5 GPU 및 Hardware

- GPU 그룹은 GPU 장치가 존재하고 `dcgm_exporter` 지표가 확인되는 경우에만 생성한다.
- 개별 GPU는 UUID 등 안정적인 장치 식별자를 기준으로 구성한다.
- IPMI/SNMP 기반 Hardware 항목은 물리 호스트에만 귀속한다.
- 물리 호스트의 온도·팬·전력 지표를 하위 VM의 지표로 복제하지 않는다.

## 6. 상태 구분

자원 실행 상태와 모니터링 상태는 분리하여 관리한다.

| 상태 | 설명 |
|------|------|
| 자원 상태 | 물리 호스트 또는 VM의 실행·중지·오류 상태 |
| 모니터링 상태 | exporter 및 최근 지표 수집의 정상·실패·미수집 상태 |

예를 들어 VM의 자원 상태가 `RUNNING`이어도 exporter가 설치되지 않았다면 모니터링 상태는 `NOT_COLLECTED`가 될 수 있다.

### 6.1 Tumblebug VM 자원 상태

Tumblebug Node의 자원 상태는 변환하지 않고 Tumblebug 상태값을 그대로 노출한다. `Terminated` 상태의 Node도 트리에서 제외하지 않는다.

| Tumblebug 상태 | 집계 버킷 |
|----------------|-----------|
| `Running` | RUNNING |
| `Creating`, `Registering`, `Reconciling`, `Suspending`, `Resuming`, `Rebooting`, `Terminating` | PENDING |
| `Suspended`, `Terminated` | STOP |
| `Failed`, `Undefined` | ERROR |

집계 버킷은 역할·Namespace·Infra·노드그룹 패널의 상태 개수 카드(running/pending/stop/error)에서만 사용하며, 트리 노드와 상세 화면에는 원래 상태값을 표시한다.

Infra 집계 상태는 `Running:1 (R:1/1)`, `Running-(3/3)`, `Partial-Failed:1 (R:1/2)` 처럼 구분자(`:` `-` `(` 공백) 뒤에 개수 접미가 붙고 `Partial-` 접두가 올 수 있다. 버킷으로 묶을 때는 접두·접미를 떼고 상태 단어만 위 표에 대조한다. `Partial-`은 Node 일부만 그 상태라는 뜻이므로 `Partial-Running`은 PENDING(혼재)으로, `Partial-Failed` 등은 뒤 단어의 버킷을 따른다. 현재 Infra 패널의 상태 카드는 Infra 집계 상태가 아니라 Node 상태를 직접 집계하므로 이 보정은 Infra 상태 자체를 버킷으로 쓸 때만 적용된다.

## 7. 조회 및 초기 로딩 원칙

- 화면 최초 로딩 시 사용자가 접근할 수 있는 전체 자원 트리를 한 번에 반환한다.
- 최초 응답에는 역할, 물리 노드, MDC, 물리 호스트, 가상자원, Tumblebug Namespace, Infra, NodeGroup 및 Node(VM)의 전체 계층을 포함한다.
- 각 자원의 exporter와 수집 지원 정보를 확인하여 노출 가능한 모니터링 항목과 GPU 장치 하위 노드도 트리에 포함한다.
- 트리 응답에는 자원의 식별 정보, 표시명, 계층 관계, 자원 상태 및 모니터링 상태 요약을 포함한다.
- 실제 사용률 및 시계열 데이터는 트리 응답에 포함하지 않는다. 사용자가 모니터링 항목을 선택하면 해당 상세 API에서 조회한다.
- 물리 호스트 하위의 1세부 가상자원과 2세부 Tumblebug 논리 계층은 서로 독립적으로 조회한 후 하나의 전체 트리 응답으로 조립한다.
- 초기 조회 성능을 위해 자원 관계 및 지원 모니터링 항목을 캐시할 수 있으며, 자원 변경이나 정해진 갱신 주기에 따라 갱신한다.

### 7.1 Tumblebug 조회 및 캐시

- 가상머신 가지는 `GET /ns` 1회와 Namespace별 `GET /ns/{nsId}/infra`(기본 옵션) 1회로 구성한다. 응답의 `node[]`에 `nodeGroupId`, `connectionName`, `connectionConfig.providerName`, `cspResourceId`, `status`, `privateIP`/`publicIP`, `spec`, `image`가 포함되므로 NodeGroup·Node 개별 조회는 하지 않는다.
- Tumblebug 조회 결과는 백엔드에서 **1분** 동안 캐시한다. 캐시 유효 시간 안의 트리 요청은 저장된 결과를 재사용하며, 자원 변경은 최대 1분 지연 후 트리에 반영된다.
- 캐시 갱신 중 Tumblebug 호출이 실패하면 마지막 정상 결과를 유지하고 가상머신 가지에 조회 실패 상태를 표시한다.

## 8. 제외 범위

현재 트리 설계에서는 다음 항목을 제외한다.

- Kubernetes Cluster, NodeGroup, Node, Pod 및 Container
- PID별 프로세스 상세 목록
- 애플리케이션 로그 및 분산 트레이스
- 물리 호스트와 VM 관계를 이름 또는 IP 주소만으로 추정하는 방식
- 1세부 가상자원과 2세부 Tumblebug VM을 동일 자원으로 연결하거나 중복 제거하는 방식

## 9. 확정된 데이터 계약

### 9.1 역할별 자원 접근 범위

- 물리 자원은 `Role → Asset.id` 관계로 연결한다. 프로젝트의 `RoleAsset` 매핑을 사용한다.
- 가상머신은 `Role → Tumblebug Namespace` 관계로 연결한다. AIMS DB의 `role_namespaces(role_id, ns_id)` 테이블로 관리하며, Tumblebug Label에는 권한 정보를 저장하지 않는다. 하나의 역할에 여러 Namespace, 하나의 Namespace에 여러 역할을 연결할 수 있다.
- 사용자의 토큰에 포함된 역할을 기준으로 두 매핑을 조회하고, 접근 가능한 자원만 전체 트리에 포함한다.
- 하나의 자원에 여러 역할이 연결된 경우에는 각 역할 가지에 표시할 수 있다. 역할을 제거한 전체 집계가 필요한 경우에는 자원 ID를 기준으로 중복을 제거한다.

### 9.2 물리 호스트와 1세부 가상화 Host 연결

- AIMS 내부 물리 호스트 참조 키는 `Asset.id`를 사용한다.
- 1세부 자산 동기화 키는 `Asset.source + Asset.externalId`를 사용한다.
- `Asset.source`는 1세부 자원 출처를 나타내고, `Asset.externalId`에는 1세부가 제공하는 불변 Host ID를 저장한다.
- 물리 호스트 하위 가상자원은 1세부 응답의 Host ID가 `Asset.externalId`와 일치할 때만 연결한다.
- Host ID가 없거나 매핑되지 않으면 hostname 또는 IP로 추정하지 않고, 해당 물리 호스트 아래의 가상자원 목록을 비워 둔다.

### 9.3 1세부 가상자원 식별자

- 1세부가 제공하는 VM UUID 또는 이에 준하는 불변 자원 ID를 `externalId`로 사용한다.
- AIMS 내부 canonical 식별자는 `SEBU1:{externalId}` 형식으로 구성한다.
- VM 이름, hostname 및 IP 주소는 표시·검색 정보로만 사용하며 식별 키로 사용하지 않는다.
- 1세부가 불변 자원 ID를 제공하지 않으면 해당 데이터 계약이 충족될 때까지 자원을 임의로 병합하지 않는다.

### 9.4 exporter 지원 및 수집 상태 판정

모니터링 항목의 지원 여부와 현재 수집 상태를 분리한다.

| 상태 | 판정 기준 | 트리 처리 |
|------|----------|-----------|
| `NOT_CONFIGURED` | 해당 exporter가 자원에 등록되지 않음 | 관련 모니터링 항목을 생성하지 않음 |
| `COLLECTING` | exporter가 등록되고 `up = 1`, 최근 샘플이 유효 시간 안에 존재 | 항목 생성 및 정상 표시 |
| `UNAVAILABLE` | exporter는 등록되어 있으나 `up = 0`이거나 최근 샘플이 유효 시간을 초과 | 기존 항목을 유지하고 미수집 표시 |
| `NO_DATA` | exporter는 정상이나 특정 장치·센서 메트릭이 한 번도 확인되지 않음 | 해당 세부 항목을 생성하지 않음 |

- 최근 샘플 유효 시간은 `max(3 × scrape_interval, 5분)`을 기본값으로 한다.
- CPU·Memory 등 항목 지원 여부는 `MonitoringTarget.exporterType`과 메트릭 카탈로그로 판단한다.
- GPU는 `dcgm_exporter` 등록뿐 아니라 해당 자원의 GPU 장치 메트릭이 확인되어야 생성한다.
- Hardware는 `ipmi_exporter` 또는 관련 `snmp_exporter`가 등록되고 센서 메트릭이 확인된 경우에만 생성한다.
- 일시적인 장애로 `UNAVAILABLE`이 되어도 기존 트리 항목을 제거하지 않는다.

### 9.5 Tumblebug connection 및 CSP 표시

- Tumblebug `connectionName`과 CSP는 트리 계층으로 추가하지 않는다.
- 가상머신 트리는 `Namespace → Infra → NodeGroup / 미분류 → Node(VM)` 구조를 유지한다.
- 트리 노드 속성에는 `providerName`만 포함한다. `connectionName`, Region, Zone 및 `location`은 상세 API에서 제공한다.
- `providerName` 값은 Tumblebug 정의를 따른다: `aws`, `gcp`, `azure`, `alibaba`, `tencent`, `ibm`, `openstack`, `ncp`, `nhn`, `kt`.
- 하나의 Infra에 서로 다른 connection 또는 CSP의 Node가 함께 존재해도 Infra를 connection별로 복제하지 않는다.

### 9.6 Tumblebug VM과 Thanos 지표 연결

- Tumblebug Node의 지표는 VM에 배포한 exporter가 Thanos로 보낸 시계열에서 조회한다.
- 연결 키는 IP가 아니라 라벨이다. exporter 등록(relabel) 시 `tb_ns`, `tb_infra`, `tb_node` 라벨을 부여하고, 트리의 `resourceId`(`TB:{nsId}/{infraId}/{nodeId}`)와 1:1로 대응시킨다.
- `privateIP`/`publicIP`를 `instance` 라벨과 대조하는 방식은 사용하지 않는다. IP는 재할당될 수 있어 §9.3의 식별 키 원칙과 충돌한다.

### 9.7 Tumblebug 자체 모니터링 API 미사용

- Tumblebug의 `/ns/{nsId}/monitoring/*` API는 CB-Dragonfly 에이전트 기반이므로 사용하지 않는다.
- Infra 생성 시 `installMonAgent`는 `no`로 지정하고, `NodeInfo.monAgentStatus`는 모니터링 상태 판정에 사용하지 않는다.

## 10. CB-Tumblebug API 대조 결과

기준: CB-Tumblebug REST API 명세(OpenAPI 3.0.1, `version: latest`, 서버 경로 `/tumblebug`), 2026-09-04 확인.

- 이 버전은 `mci`, `subGroup`, `vm` 용어를 사용하지 않고 `infra`, `nodegroup`, `node`를 사용한다. 본 문서의 `nodeGroupId`와 `/ns/{nsId}/infra` 경로는 명세와 일치한다.
- 사용 API

| 용도 | API | 비고 |
|------|-----|------|
| Namespace 목록 | `GET /ns` | `option=id`로 ID만 조회 가능 |
| Infra·NodeGroup·Node 일괄 조회 | `GET /ns/{nsId}/infra` | 기본 옵션 응답 `infra[].node[]` 사용, `option=status`는 `nodeGroupId`가 없어 사용하지 않음 |
| Node 단건 상세 | `GET /ns/{nsId}/infra/{infraId}/node/{nodeId}` | 상세 API에서만 사용 |
| CSP 연결 정보 | `GET /connConfig` | `providerName`, `regionDetail` |

- 사용 필드: `NsInfo.id/name/uid`, `InfraInfoSummary.id/name/status/statusCount/node[]`, `NodeSummary.id/name/uid/nodeGroupId/status/connectionName/connectionConfig.providerName/cspResourceId/privateIP/publicIP/spec(vCPU, memoryGiB, accelerator*)/image(osType)`.
- Tumblebug Node 상태값: `Creating`, `Registering`, `Reconciling`, `Running`, `Suspending`, `Suspended`, `Resuming`, `Rebooting`, `Terminating`, `Terminated`, `Failed`, `Undefined`.
- Kubernetes 관련 API(`/ns/{nsId}/k8sCluster*`)는 §8에 따라 사용하지 않는다.
