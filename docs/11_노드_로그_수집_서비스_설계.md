## 1. 목적과 범위

관측 > 자원 탐색기 > 노드 상세의 로그/트레이스 탭에서 수집 희망 설정을 등록하고,
그 설정에 연결된 파일 경로의 로그를 조회한다.

- 구현: 수집 서비스 관리 4종, 후보 탐지·위저드 검증 2종, 서비스 로그 조회 4종.
- 미지원(501): 기존 트레이스 조회.
- 후보 탐지와 검증의 관측 원천은 Loki 뿐이다. 호스트 프로세스·포트·파일 존재·권한은 보지 않는다.
- 제외: 수집기 설정 반영, VM 수집기 배포, 공용 로그에서 특정 서비스 분리, Tempo/계측 도입.
- 이 원장은 실행 중인 프로세스 목록이나 수집기 적용 상태를 증명하지 않는다.

관련 문서: [수집 SW](03_자원_수집_SW_설치_및_인터페이스_분석.md),
[트리](06_자원_탐색기_트리_설계.md), [알람](09_알람_설계.md).

## 2. 수집 경로와 현황

```text
노드 파일 → Alloy(Promtail 후속) → Loki → AIMS API → 화면
수집 희망 설정 → AIMS DB (수집기로 자동 반영되지 않음)
```

메트릭 저장 경로는 node_exporter → Prometheus → Thanos다.
로그 건수 같은 집계는 Loki에서 LogQL로 계산한다.

운영 관측(2026-09-28): 수집기는 Grafana Alloy v1.20.0, k8s-cp 1대, syslog/auth.log/kern.log 수집 중,
aims-app은 파일 미생성 상태. 2026-09-28 Promtail에서 Alloy로 교체했다(§7.3).
저장소의 `deploy/monitoring/config.alloy`가 아래 경로를 설정한다.

| job | 경로 |
|-----|------|
| syslog | /var/log/syslog |
| auth-log | /var/log/auth.log |
| kern-log | /var/log/kern.log |
| aims-app | /var/log/aims/*.log |

애플리케이션 파일 로깅(`LOGGING_FILE_NAME`) 외에도 파일 권한, 디렉터리, 수집기 마운트가 맞아야 수집된다.
수집기 glob과 원장 경로 문법은 다르다. 원장은 정확한 파일 경로만 허용한다.

## 3. 라벨 규약과 접근 제어

| 라벨 | 출처 / 의미 |
|------|-------------|
| instance | 수집기 external_labels. 해당 노드의 node_exporter scrape_endpoint와 동일하게 배포 |
| mdc_id | 수집기 external_labels. ScopedHost.mdcId와 동일하게 배포 |
| filename | 파일 수집기의 실제 파일 경로 |
| job | 수집 설정의 묶음 |
| level | 파이프라인에서 추출. 없는 경우 미분류 |

`Asset.id → ScopedHost(instance, mdcId)`를 사용하고 모든 조회에 두 라벨을 강제한다.
메트릭과 로그의 라벨 일치는 자동 보장이 아닌 배포 계약이다.
운영에서는 실제 값을 명시하며 `localhost:9100/mdc-local` 기본값의 복제 배포를 금지한다.
전체 노드에서 (mdc_id, instance)는 고유해야 한다. 주소 변경 시 과거 라벨 이력 조회는 이번 범위 밖이다.

- NodeAccessService가 현재 토큰 역할 스코프와 Asset 존재를 검증한다. 없거나 스코프 밖이면 404.
- 서비스는 항상 id와 asset_id를 함께 조회한다. 다른 노드의 서비스 ID는 404.
- instance/mdc_id를 결정할 수 없으면 미설정. 조건을 제거하여 조회하지 않는다.
- Loki 라벨 목록에 값이 없다는 이유로 미설정으로 판단하지 않는다. 정상 설정에 로그가 없을 수도 있다.
- 후보 탐지/검증도 먼저 노드 스코프를 검사한다. 라벨 매핑이 없으면 후보는 빈 목록, 검증 관측은 UNKNOWN.
- 파일 필터는 원장에 등록된 전체 경로만 허용한다. 서비스 밖의 파일은 400.

수집기 설정은 `loki.write`의 external_labels로 instance·mdc_id를 붙이며, 값은 compose environment(NODE_INSTANCE, MDC_ID)에서 읽는다.
Promtail 때(clients.external_labels)와 같은 계약이다.
공용 로그는 filename만으로 특정 서비스를 구분할 수 없다. 추후 본문 파싱/서비스 식별 라벨로 확장 가능하다.

## 4. 원장 스키마와 검증

### 4.1 collect_services

| 컬럼 | 타입 / 제약 |
|------|-------------|
| id | bigserial PK |
| asset_id | bigint NOT NULL, assets(id) FK ON DELETE CASCADE |
| service_name | varchar(200) NOT NULL, trim 후 공백 금지 |
| description | varchar(500) |
| log_enabled / syslog_enabled / trace_enabled | boolean NOT NULL DEFAULT false |
| created_by | varchar(200), 인증 사용자 이메일 |
| created_at / updated_at | timestamptz NOT NULL |

UNIQUE(asset_id, service_name). 앞뒤 공백을 제거하고 대소문자는 구분한다. 중복은 409.
생성자는 요청에서 받지 않는다. 등록·수정 시각은 서버에서 생성한다.

### 4.2 자식 테이블

| 테이블 | 컬럼 / 제약 |
|--------|-------------|
| collect_service_log_paths | service_id FK CASCADE, path varchar(500) NOT NULL, PK(service_id,path) |
| collect_service_trace_ports | service_id FK CASCADE, port integer 1~65535, PK(service_id,port) |

JPA element collection으로 저장하며 배포 SQL에서는 복합 PK로 중복을 제한한다.
생성·수정은 부모와 자식을 한 트랜잭션으로 저장한다. PUT은 전체 설정 교체다.
같은 요청의 중복 경로/포트는 하나로 저장한다.

### 4.3 입력 정책

- 로그 경로: 최대 100개, 각 500자 이하, 절대 파일 경로, 제어문자 및 glob(* ? [ ] { }) 금지.
- 로그 enabled=true이면 경로 1개 이상. 파일 존재/읽기 권한은 검사하지 않는다.
- syslog_enabled=true이면 log_enabled=true여야 한다. Syslog 토글만으로 경로를 자동 추가하지 않는다.
- 트레이스 포트: 최대 100개, 각 1~65535. 수집기 적용이나 포트 관측을 의미하지 않는다.
- 모든 토글을 끄는 설정도 허용한다. 기존 경로/포트의 보존은 PUT payload에 따른다.
- 비활성화 상태에서도 등록된 경로의 과거 로그를 조회할 수 있다.

## 5. API 계약

접두: `/api/v1/monitoring/resource-explorer/node/{nodeId}`

| API | 동작 |
|-----|------|
| GET /services | 검색·정렬·페이징 + 노드별 1회 Loki 최근 로그 관측 |
| POST /services | 원장 생성 |
| PUT /services/{serviceId} | 원장 전체 설정 교체 |
| DELETE /services/{serviceId} | 원장과 자식만 삭제 |
| GET /services/discovered | 수집기가 최근 24시간 동안 이 노드에서 Loki로 보낸 job·파일을 후보로 반환 |
| POST /services/validate | 입력 규칙 검증(issues) + 로그 경로별 최근 24시간 관측(observations) |
| GET /services/{serviceId}/logs/files | from/to 기간의 등록 파일 목록과 건수 |
| GET /services/{serviceId}/logs/summary | file 필터, 기간 건수와 최근 로그 상태 |
| GET /services/{serviceId}/logs/trend | files·interval·from/to |
| GET /services/{serviceId}/logs | files·levels·keyword·limit·from/to |
| GET /services/{serviceId}/traces/summary | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/trend | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/methods | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/endpoints | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/ports | 접근 검증 후 501 |
| GET /services/{serviceId}/traces | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/{traceId} | 접근 검증 후 501 |
| GET /services/{serviceId}/traces/{traceId}/logs | 접근 검증 후 501 |

트레이스 8종은 노드 스코프 및 서비스 소속 검증을 먼저 수행한다. 없거나 다른 노드 소속이면 404,
검증 통과 시 BusinessException으로 공통 ApiResponse 오류 본문의 501을 반환한다.
트레이스 데이터가 없어 traceId의 실재 여부는 검사하지 않는다.

모든 API는 SecurityConfig에서 인증을 요구한다. 생성은 created_by 저장을 위해 인증 주체 이메일을 추가 확인하며 확인 불가 시 401이다.
수정·삭제에도 HTTP 인증과 노드/서비스 접근 검증이 적용된다. 생성에만 있는 이메일 검사가 무인증 수정 허용을 의미하지 않는다.

생성·수정·삭제에 @PortalLog, refType=COLLECT_SERVICE를 사용한다.
쓰기 API는 Loki를 호출하지 않는다. 저장 직후 logStatus는 미관측 UNKNOWN 또는 미설정 UNCONFIGURED이며 목록 재조회로 관측한다.

목록: page는 1부터, size=1~100, keyword는 서비스명 대소문자 무시.
sort는 serviceName/description/logStatus/serviceId와 asc/desc 조합. 기본 serviceName,asc.
logStatus 오름차순은 이름 알파벳순(NO_RECENT_LOGS → RECENT_LOGS → UNCONFIGURED → UNKNOWN)이며 내림차순은 역순이다.
장애 심각도 순서가 아니다. 동률은 serviceId 문자열 오름차순으로 정렬한다.
PID·관측 포트·서비스 실행 status는 null이다.
capabilities는 실제 지원 여부가 미확정이므로 빈 목록이다. 선택한 기능은 logCollection/traceCollection으로 확인한다.

### 5.1 DTO 변경

- CollectServiceValidationResponse: observations 추가 — `{path, status}` 목록, status는 OBSERVED / NOT_OBSERVED / UNKNOWN.
  valid는 입력 규칙만 반영하며 관측 결과에 영향받지 않는다.
- DiscoveredServiceResponse: 구조 변경 없음. description에 "최근 24시간 수집 파일: 경로 (건수), …"를 실어 2단계 경로 입력 힌트로 쓴다.

- CollectServiceResponse: 기존 status는 실행 상태(null)로 유지, logStatus 추가.
- ServiceLogSummaryResponse: collectStatus 필드명은 유지하고 LogStatus enum 적용, unknownCount 추가.
- ServiceLogFileResponse: fileName은 path의 마지막 '/' 뒤 basename이다. 조회 키는 전체 path다.
  서로 다른 디렉터리의 동명 파일은 같은 fileName으로 표시될 수 있으므로 화면에서는 path를 함께 표시하여 구분한다.
- ServiceLogLevel: UNKNOWN 추가. WARN/WARNING 및 대소문자 정규화.
- ServiceLogTrendResponse.Bucket: unknownCount 추가. timestamp는 버킷 시작(UTC Unix 초).
- ServiceLogListResponse: totalCount는 동일 필터의 별도 집계, entries는 최대 limit건.

프런트엔드는 위 필드 추가와 미분류 범례를 반영해야 한다.
capabilities가 비어 있다는 것은 실제 지원 없음이 아니라 미확정이라는 계약이다.

### 5.2 후보 탐지와 위저드 검증

후보 탐지(`GET /services/discovered`):
- 질의: `sum by (job, filename) (count_over_time({instance, mdc_id}[86400s]))` 1회. job 라벨별로 묶어 serviceName으로 쓰고,
  job이 없는 스트림은 파일 basename을 이름으로 쓴다. 이름순 정렬.
- PID·포트는 null, capabilities는 LOG만. 이미 등록된 이름도 후보에 남긴다(편집 위저드가 같은 목록으로 현재 서비스를 표시).
- 라벨 매핑이 없으면 빈 목록(Loki 호출 없음). Loki 실패는 목록 조회와 달리 502로 올린다 — "후보 없음"과 "조회 실패"를 화면이 구분해야 한다.

위저드 검증(`POST /services/validate`):
- issues: 이름·설명 길이, Syslog 토글 종속, 경로 개수·형식(glob 없는 절대 경로), 포트 개수·범위.
  field는 요청 JSON 경로(`serviceName`, `description`, `logCollection.syslogEnabled`, `logCollection.logPaths`, `traceCollection.ports`).
  저장 API의 400 메시지와 같은 규칙(`issues()`)을 공유한다.
- 이름 중복은 검사하지 않는다. 편집 위저드도 같은 API를 부르므로 자기 이름과 구분할 수 없다. 저장 시 409.
- observations: valid=true일 때만 로그 경로(중복 제거, 정렬)별 최근 24시간 건수를 관측해 OBSERVED / NOT_OBSERVED를 준다.
  라벨 매핑 미설정 또는 Loki 502는 UNKNOWN이며 valid에 영향 없다. 아직 수집되지 않는 파일을 등록하는 것이 이 기능의 목적이다.

## 6. 조회와 상태

### 6.1 선택자 / 문자열 처리

```logql
{instance="10.0.0.11:9100", mdc_id="mdc-01", filename="/var/log/syslog"}
{instance="10.0.0.11:9100", mdc_id="mdc-01", filename=~"(/var/log/a\\.log|/var/log/b\\.log)"}
```

단일 경로는 =, 다중은 각 리터럴의 정규식 메타문자를 escape한 OR다.
LogQL 라벨 정규식은 전체 일치이므로 별도 앵커는 불필요하다.
정규식 escape 후 LogQL 문자열의 역슬래시/큰따옴표/제어문자를 별도로 escape한다.
사용자가 LogQL이나 정규식을 직접 전달하는 API는 제공하지 않는다.

### 6.2 시간과 제한

- from/to: ISO-8601 Instant. 잘못된 형식은 400. 기본은 서버 시간대의 오늘 00시와 현재.
- 소수 초는 초 단위로 내림한다. 유효 기간 1초~30일. 초과 시 Loki 호출 전 400이다.
- 배포 Loki max_query_length=720h, retention_period=30d와 맞춘다. 조회 길이 제한과 보존 기간은 별개이며 오래된 날짜의 짧은 조회는 정상 빈 결과가 될 수 있다.
- 모든 집계/목록은 **(from, to]**, 시작 제외·종료 포함. 인접 기간의 경계 로그가 중복되지 않는다.
- Loki 스트림은 [start,end)이므로 from+1ns, to+1ns를 전달한다.
- interval: 1m/5m/15m/1h/6h/1d, 기본 1h. 최대 1000버킷.
- 목록 limit=1~1000, 기본 100. keyword 최대 1000자, 리터럴 포함 검색.
- Loki 연결 제한 3초, 읽기 제한 10초. 서버 오류/형식 불일치/타임아웃은 502.
- 매핑 미설정 상태에서 로그 조회는 409. 정상 조회 결과 없음과 구분한다.
- 목록은 모든 스트림을 합쳐 시간 역순 정렬한다. 후속 페이지 커서는 이번 범위 밖이다.

### 6.3 질의

| 대상 | LogQL / 처리 |
|------|-------------|
| 파일별 건수 | sum by (filename) (count_over_time({sel}[기간])) |
| 레벨별 건수 | sum by (level) (count_over_time({sel}[기간])) |
| 전체 검색 건수 | sum(count_over_time({sel} &#124;= "검색어" [기간])) |
| 로그 목록 | 집계와 같은 파일·레벨·검색어 필터, direction=backward |

파일 목록은 원장 기준이다. 기간 내 로그가 없는 등록 파일도 0건으로 표시한다.
레벨 없음/지원하지 않는 레벨은 UNKNOWN으로 합산한다. 총건수에는 모두 포함한다.
WARN과 WARNING은 WARNING으로 합친다. TRACE/FATAL 등 별도 분류가 없는 값도 UNKNOWN이다.
UNKNOWN 필터는 지원 레벨이 아닌 값과 라벨 없는 로그를 포함한다.

추이는 전체 조회 기간을 매번 집계하지 않는다.
예: 1분 간격이면 [60s]를 step=60으로 평가하고 평가 시각에서 60초를 빼 버킷 시작으로 응답한다.
from을 기준으로 버킷을 나누고, 마지막 부분 버킷은 남은 초만 별도 instant query로 집계한다.
정상 응답에 없는 버킷은 0으로 채운다. 오류를 0으로 채우지 않는다.
조회 도중 로그가 추가되면 별도 요청인 KPI/목록/추이가 완전히 같은 스냅샷은 아닐 수 있다.

### 6.4 logStatus

| 값 | 판정 |
|----|------|
| UNCONFIGURED | 원장 경로 없음 또는 instance/mdc_id 결정 불가 |
| UNKNOWN | Loki 오류/타임아웃, 또는 쓰기 응답의 미관측 상태 |
| RECENT_LOGS | 최근 5분 중 등록 경로 하나 이상에 로그 있음 |
| NO_RECENT_LOGS | 조회 성공, 등록 경로에 최근 로그 없음 |

서비스 실행 정상 여부가 아니다. 과거 기간을 조회해도 상태는 현재 기준 최근 5분이다.
KPI의 file 필터는 건수에만 적용한다. collectStatus는 서비스 전체 등록 경로를 기준으로 판정하여 목록의 logStatus와 같은 범위를 사용한다.
단, 두 요청 사이에 로그가 추가되거나 5분 창에서 빠지면 시점 차이로 상태가 달라질 수 있다.
토글 값과 독립적이며 트레이스만 등록하여 경로가 없으면 UNCONFIGURED다.
목록에서는 노드 선택자로 1회 집계하여 경로별 결과를 각 서비스에 매핑한다.
빈 서비스 목록/경로 없음/식별자 없음이면 Loki를 호출하지 않는다.

## 7. 한계와 운영 과제

### 7.1 원장과 적용 상태

등록·수정은 수집 희망 설정만 저장한다. 수집기 적용 여부는 확인되지 않는다.
토글 비활성화로 로그 전송이 멈추지 않으며, 삭제해도 기존 Loki 로그는 남는다.
기존 수집 경로로 기능을 검증하되 새 경로 반영은 별도 과제다.

### 7.2 인제스트 제한

초안 관측값(2026-09-10): rate_limited 폐기 누적 약 89,000건.
이 누적값만으로 현재 장애나 제한 상향 필요성을 단정하지 않는다.
관측 기간의 증가율, 유입량, 순간 폭주/재전송, 서버 자원을 확인한 뒤
ingestion_rate_mb/ingestion_burst_size_mb 및 수집량을 조정한다.

### 7.3 Promtail → Alloy (2026-09-28 완료)

Promtail은 2026-03-02 지원 종료. 2026-09-28 k8s-cp에서 Grafana Alloy v1.20.0으로 교체했다.
배경과 절차는 Confluence "Promtail → Grafana Alloy 전환 배경 및 계획"에 있다.

- 변환: `alloy convert --source-format=promtail`로 promtail.yml을 옮긴 뒤 세 곳을 손봤다.
  external_labels를 `coalesce(sys.env(...), 기본값)`으로, stage.multiline을 Promtail 기본값(128줄·3s)으로 명시,
  `legacy_positions_file`로 Promtail positions 이관.
- compose: promtail 서비스를 alloy 서비스로 교체. 환경 변수 이름(NODE_INSTANCE, MDC_ID)과 /var/log 마운트는 유지.
  Promtail의 positions.yaml을 `docker cp`로 `./alloy-legacy/`에 복사해 첫 기동 때 읽기 위치를 이어받았다.
- 검증: 4개 job 모두 positions 이관 성공, Loki 라벨(job 3종, instance, mdc_id) 전환 전과 동일, 5분 적재 건수 정상.
- 저장소의 promtail.yml은 삭제했다. 롤백이 필요하면 커밋 이력(7577036 이전)에서 복원한다.

같은 날 `compose up`이 Thanos receive·store·compactor를 named volume 설정으로 재생성하면서 저장소가 비는 사고가 있었다.
운영 서버는 `./data` bind mount를 쓰므로 compose를 그에 맞게 정정했다(abe814f). 배포 시 compose와 실행 중 컨테이너의 불일치를 먼저 확인한다.

Alloy 설치만으로 원장 경로가 자동 반영되지는 않는다. 수집 대상 자동 반영은 노드별 file_sd JSON API +
Alloy `discovery.file` + 노드 cron 구성(권장)으로 후속 작업한다.
원격 설정(`--config.file=http://...`)은 설정 제공 서버, 인증, 폴링/적용, 오류 시 이전 설정 유지와 롤백 설계가 필요해 노드가 늘어난 뒤 검토한다.

| 미결 항목 | 후속 작업 |
|-----------|-----------|
| 후보 탐지 확장 | 현재는 Loki에 이미 들어온 파일만 후보. 아직 수집 전인 서비스는 프로세스·포트·systemd 유닛 관측 수단이 있어야 후보가 된다(k8s-cp node_exporter에 `--collector.systemd` 미적용) |
| 호스트 경로 검증 | 파일 존재·권한 확인 수단. 현재 검증은 형식 규칙과 Loki 관측뿐 |
| 신규 경로 적용 | 노드별 file_sd JSON API + Alloy `discovery.file` + 노드 cron (§7.3) |
| VM 로그 | Tumblebug VM 수집기 배포 |
| 트레이스 | 계측·저장소 결정 |
| 안정적 노드 라벨 | 주소 변경/중복 방지를 위한 asset_id 기반 라벨 및 이력 매핑 검토 |

## 8. 구현 구성과 배포

- NodeAccessService: 기존 노드 패널과 로그 서비스의 접근 검증 공통화.
- CollectService / CollectServiceRepository: 원장과 자식 컬렉션.
- ResourceExplorerNodeLogService: 원장 관리, 입력·파일 스코프 검증, 응답 조립.
- NodeLogQueries: 안전한 선택자, 상태/레벨 집계, 버킷 및 검색.
- LokiQueryClient: streams/vector/matrix 분리, 시각 지정, 실패·타임아웃 처리.
- 배포 SQL: deploy/sql/2026-09-11_collect_services.sql.

기존 운영 DB에는 배포 SQL 적용이 필요하다. 이번 작업은 저장소 구현이며 운영 DB 적용/배포를 수행하지 않는다.
수집기 라벨과 ScopedHost 값을 배포 환경에서 대조한 뒤 기존 수집 파일로 연동 검증한다.

검증 대상: 스코프/다른 노드 서비스 404, 파일 선택 제한, 원장 CRUD/중복/자식 삭제,
문자열 escape, WARN/미분류, 장애와 무로그 구분, 최근 상태 일괄 조회,
버킷 경계·부분 버킷·0 채움, totalCount와 limit 분리, Loki 응답 파싱.
